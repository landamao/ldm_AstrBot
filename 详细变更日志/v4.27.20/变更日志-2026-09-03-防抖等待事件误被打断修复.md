# [2026-09-03] 消息防抖等待中的事件误被打断修复

> 本文件为独立变更日志，记录 2026-09-03 一次消息防抖与「打断旧回复」逻辑
> 的交互修复：私聊连发消息（尤其图片）时，防抖合并完成后不请求 LLM、
> 直接无回复的问题。配套回归测试
> `tests/test_debounce_interrupt_interaction.py`（4 个用例）。

---

## 问题现象

私聊连发消息（两张图片、或图片+文字、或快速连发文字）时，看起来「有发送
图片的话，会导致不请求 LLM，直接就没了」：

- 收到消息后防抖正常合并（日志「消息防抖: 合并 N 条消息后继续」）；
- 图片描述请求（mini 模型）正常返回；
- 但随后主对话请求（pro 模型）刚发起就被停止，日志表现为：

```
正在请求 LLM，使用模型: 豆包/doubao-seed-2-0-pro（提供商: ldmapi）
Agent execution was requested to stop by user.
停止时未发送任何内容，跳过历史裁剪与停止标记
Agent 用量: 输入 0 | 输出 0 | 合计 0 | ... | 状态 已中断
```

最终用户收不到任何回复。文字消息同样会触发，只是时序上不一定每次必现。

## 根因

处理链路的时序是「**先打断旧回复，再进入消息防抖**」（为保证打断及时、
静默窗口期间旧回复不再分段发送）：

1. 首条消息进入管线即被 `active_event_registry` 注册为活跃事件；
2. 首条进入防抖等待（开 2s 窗口）；
3. 窗口内第二条消息到达，执行打断判断：此时没有活跃 runner，
   但首条事件仍在注册表里，`has_active` 判定为 True，于是
   `request_agent_stop_all` 把**防抖等待中的首条事件**当成「旧回复」
   打上了 `agent_stop_requested` + `agent_user_aborted` 标记
   （日志「打断当前回复: 停止请求数=1, 有活跃runner=False」；
   「停止请求数=1」停的正是防抖中的事件本身）；
4. 防抖窗口结束，首条合并全部消息后继续走 agent runner；
5. runner 检查到 `agent_stop_requested` 标记 → 立即中止，
   请求 LLM 前就退出，用量全 0。

防抖等待中的事件还没有开始任何回复，本就不该被当作「旧回复」打断。

## 修复内容

保持「先打断后防抖」的顺序不变（打断及时性不受影响），改为让打断逻辑
识别并跳过**防抖等待中**的事件：

- `internal.py::_message_debounce_wait`：首条事件进入防抖等待时设置
  `event.set_extra("agent_debounce_waiting", True)`，
  `finally` 统一清除该标记（合并放行、异常、被 reset 等路径都会走 finally）；
- `active_event_registry.py::has_active`：跳过带 `agent_debounce_waiting`
  标记的事件——只有「真正在跑的回复」才算活跃回复，仅防抖等待时不再触发打断；
- `active_event_registry.py::request_agent_stop_all`：跳过带
  `agent_debounce_waiting` 标记的事件——打断只标记真实旧回复，
  防抖等待中的新消息不再被误停；
- 注意：`stop_all()`（/reset 等场景）**不改**，仍会停止包括防抖等待
  在内的一切事件，保证 reset 语义不受影响。

效果：防抖合并结束后首条事件不带任何停止标记，正常请求 LLM 并回复；
同时旧回复的打断依旧及时（先打断后防抖），分段回复不会继续发。

## 验证

- 新增 `tests/test_debounce_interrupt_interaction.py` 4 个用例：
  - 打断的 request_agent_stop_all 跳过防抖等待事件（不被标记停止）；
  - 仅防抖等待事件时 has_active 为 False（不触发打断）；
  - 旧回复 + 防抖等待并存时 has_active 仍为 True（旧回复可打断）；
  - has_active 的 exclude 语义不受影响；
- 原有消息防抖 10 个用例 + 打断 2 个用例全部保持通过；
- 合计 16 个用例通过，无回归。

## 部署 / 测试注意

- 纯后端改动，不涉及前端，**无需执行 `~/构建部署.sh`**；
- 将 `internal.py`、`active_event_registry.py` 同步到运行目录后重启
  ldm 生效；
- 行为变化点：防抖等待期间到达的新消息不再触发「已打断当前回复」的
  通知提示（本来也没有旧回复可打断），合并后一次性回复，体验符合预期。

单文件级回滚：恢复 `internal.py` 与 `active_event_registry.py` 旧版本并
重启即可；测试文件可删可留。回滚后回到「防抖合并的消息可能被误停止」的
旧行为。
