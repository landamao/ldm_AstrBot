# [2026-08-30] 工具轮次落库修复 与 工具图片处理重做

> 本文件为独立变更日志，记录 2026-08-30 一次联排修复：会话历史整轮丢失的落库 bug，
> 以及工具生成图片的上下文注入策略重做（跟随「始终使用默认图片转述模型」全局配置）。

---

## 问题现象

QQ（aiocqhttp / NapCat）群里让 bot 生图，图片能发出来，但：

- **对话数据里查不到这一轮**，历史停在一个较早的时间点，中间凭空缺若干轮；
- 追问 bot「刚刚干了什么」，它完全不知道，自述"上一条直接跟我说的还是昨晚"；
- 之后普通的文本问答轮次又能正常落库。

服务器日志佐证（10:13 生图轮 / 10:19 改图轮）：
两轮均以 `send_message_to_user 没有返回值，或者已将结果直接发送给用户` WARN 收尾，
后续轮次上下文从 148.93k 骤降回 72.49k，证明事故轮次从未进入持久化历史。

## 根因

### 1. 整轮不落库（主因）

`internal.py` 的 `_save_to_history` 中，`conv_manager.update_conversation(...)`（落库调用）
被错误地缩进在 `if isinstance(checkpoint_id, str) and checkpoint_id:` 块内。
而 `llm_checkpoint_id` extra **只有 WebChat 适配器会设置**，QQ 等其他平台恒为 None，
导致分支直接 `return`：

- 工具返回 None 结束循环的轮次（如 `send_message_to_user` / `send_onebot_msg` 默认行为），
  此时 `final_llm_resp` 为 None，正好命中该分支 → **整轮静默丢弃**；
- LLM 请求报错（role=err）的轮次 → 同样不落库，用户消息也随之丢失。

该分支注释本意（#9358）是"LLM 失败时仍保留消息便于续写"，缩进让它在非 WebChat 平台
退化成了"整轮丢弃"。

### 2. 工具图片处理不合理（次要，但本次一并重做）

工具返回图片时，runner 会把图片 base64 回注进上下文供模型"审查"，判定条件是
`modalities 未配置 = 支持图片`。导致：

- ldmapi 的 glm-5.2 渠道不支持图片输入，收到回注图片直接 400
  （`Model do not support image input`），触发 provider 回退、翻倍消耗 token；
- 回注的大图 base64 还会写进对话历史，持续膨胀上下文。

## 修复内容

### 修复一：所有平台无条件落库

`_save_to_history` 的兜底分支（`llm_response is None` 或 `role != "assistant"` 且非打断）
中，`update_conversation` 移出 `checkpoint_id` 判断：checkpoint 段的追加保留在 if 内
（WebChat 行为不变），**落库调用对所有平台执行**。工具发送消息轮、LLM 报错轮的用户消息
与工具调用记录不再丢失。

### 修复二：工具图片跟随收图路径的全局配置

工具生成的图片与用户发来的图片走**同一套**模态/转述配置逻辑：

| 配置状态 | 图片给 LLM 的方式 | 图片怎么发给用户 |
|---|---|---|
| 模型支持图片输入（modalities 含 `image`，或迁移空列表）**且**未开「始终使用默认图片转述模型」 | 原图回注进上下文，模型可审查 | LLM 审查后手动调 `send_message_to_user`（原流程，不变） |
| 模型不支持图片，**或**开启「始终转述」 | 不回注原图；先用「默认图片转述模型」（收图同款配置：`image_caption_prompt`、`image_compress_*`）生成描述，以 `<image_caption>…</image_caption>` 写进工具结果 | 工具结果提示语给出明确指引，由 **LLM 手动**调 `send_message_to_user`（type='image', path=…）发送 |
| 不支持图片且未配转述模型 | 工具结果只有路径 + 发送指引（无内容描述，框架无从得知图片内容） | 同上，LLM 手动发送 |

效果：ldmapi 这类不支持视觉的渠道不再收到 base64 大图（消除 400 与无谓回退），
上下文不再被工具图片撑爆；生图轮的图片内容经转述进入上下文，LLM 能"看图说话"。

**明确不变的行为**：图片一律由 LLM 手动调用发送工具发出，框架不代发（自动发送方案已否决并移除）。

### 重构：消除判定与压缩的重复实现

- 模态判定统一为 `provider/modalities.py:provider_supports_modality`（收图路径
  `astr_main_agent` 与工具图片 runner 共用；保留 `[]` 迁移兼容语义，`None` 视为不支持）；
- 图片压缩配置解析与压缩实现统一下沉到 `utils/media_utils.py`
  （`get_image_compress_args` / `compress_image_for_provider` / `compress_images_for_provider`），
  删除 `astr_main_agent.py` 与 `tools/image_tools.py` 各自的重复副本。

## 部署 / 测试注意

- 复制后重启 bot 生效（Python 会重新编译，无需手动清 `__pycache__`）；
- 服务器如为 v4.27.14、本地仓库 4.27.13，覆盖前先比对这几个文件的既有差异，
  尤其是 `internal.py` 与 `tool_loop_agent_runner.py`；
- 未配「默认图片转述模型」时，生图轮 LLM 只拿到路径+发送指引，说不出图片内容；
  配置后自动走 `<image_caption>` 分支，无需改代码；
- 事故期间（修复前）已丢失的历史轮次无法追回，修复后新轮次正常落库。
