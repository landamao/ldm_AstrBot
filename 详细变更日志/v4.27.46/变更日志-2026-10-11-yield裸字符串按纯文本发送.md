# [2026-10-11] handler 产出裸字符串按纯文本发送

> 本文件为独立变更日志，记录 `yield "文本"` / `return "文本"` 自动按 `plain_result` 处理的实现落点、作用域边界与工具链路不受影响的论证。

---

## 动机

插件指令里回一句纯文本，此前必须写全 `yield event.plain_result("文本")`；直接 `yield "文本"` 会走 `call_handler` 的 else 分支被原样上抛、ProcessStage 忽略，**静默无效**——不报错、不发送，很容易踩。定案：裸字符串视作纯文本结果，等价于 `event.plain_result(ret)`。

```python
@filter.command("屏蔽该群", alias={"屏蔽此群", "拉黑此群"})
async def 屏蔽该群指令(self, event: AstrMessageEvent):
    yield "已屏蔽本群，后续消息不再响应。"   # 现在可以直接这样写
```

注意 handler 仍须是 `async def`（同步生成器本就不被支持，现状未变）。

## 实现（astrbot/core/pipeline/context_utils.py 的 call_handler）

`call_handler` 的两个分支各加一个 `isinstance(ret, str)` 判断，命中则 `event.set_result(ret)` 后 bare `yield`：

- 异步生成器分支：`yield "文本"` → set_result → 与 `yield event.plain_result("文本")` 完全同路；
- 协程分支：`return "文本"` → 同上（非生成器 handler 的对称行为，此前 `return` 裸串同样静默无效）。

`set_result` 本就接受 `str`（内部转 `MessageEventResult().message(result)`），本次未改 `set_result`，转换只有一处。多次 yield 时后者覆盖前者，与连续 plain_result 的既有语义一致；空串/纯空白走 respond 阶段既有的空白链过滤，不会发出空消息。

## 作用域边界：LLM 工具链路不受影响

全仓 `call_handler` 唯一调用点是 `process_stage/method/star_request.py`（消息 handler 链路）。LLM 工具执行走 `agent/tool_executor.py` → `tool_loop_agent_runner.py` 的独立链路，「工具 `return str` → 加入下一次 LLM 请求 prompt」的既有语义（`register_llm_tool` docstring 所载）不被本改动触及。钩子（`call_event_hook`）返回值本就被忽略，同样不受影响。

其余产出类型行为不变：`MessageEventResult`/`CommandResult` 照旧，`ProviderRequest` 等其他类型照旧原样上抛（ProcessStage 按 LLM 请求处理）。

## 兼容性

- **纯增量**：此前 `yield "字符串"` 是静默无效（不发送），现在会发送。若有插件依赖「yield 字符串什么都不发生」的反直觉行为（合理推断无人依赖），行为有变；其余场景零影响。
- 工具返回 str 进 prompt 的语义、钩子、其他产出类型均不变。

## 测试（tests/test_yield_plain_str.py，7 用例全过）

yield 裸串与 return 裸串落结果且不透传、yield None 仍无结果、MessageEventResult 老写法（yield 与 return 两路）回归、ProviderRequest 原样上抛不被误包、多次 yield 后者覆盖。全量回归 408 项全过。

## 回归点

- `set_result` 对 str 的转换是唯一包装点，`call_handler` 只做类型识别；别在适配器或 respond 阶段再加一层字符串特判。
- 新增 handler 产出类型（如想让 `MessageChain` 直发）时在 `call_handler` 两个分支同步扩展，并同步本文档与测试。
