# 变更日志 — 2026-10-30 — 事件收尾钩子 OnEventCompletedEvent

## 背景

插件想在「机器人开始思考」时给用户消息贴个表情作为反馈（`on_waiting_llm_request` / `on_llm_request` 里调
`set_msg_emoji_like`），但贴出去之后没有任何时机撤销：一旦这条消息最终没有回复，表情会一直挂在用户消息上，
看起来像机器人卡住了。

排查后确认框架侧缺一环：

1. `EventType` 里没有任何「事件结束 / 事件被终止」类型，最接近的 `OnAfterMessageSentEvent` 只在真的发出消息时触发。
2. `call_event_hook()` 自 4.27.45 起有入口预检：`event.is_stopped()` 为真时直接 `notify_event_stopped()` 返回，
   **一个处理器都不执行**，处理器之间的终止检查同样会提前返回。也就是说事件被终止后，插件收不到任何钩子。
3. `notify_event_stopped` 只写日志、给 WebChat 推终止卡片，不对外暴露。
4. `PipelineScheduler.execute()` 的 `finally` 只做临时文件清理与活跃事件注销，没有插件回调点。

结论：要让插件能收尾，必须在框架侧补一个「事件处理完成」的派发点。

## 改动

### 1. 新增事件类型（`astrbot/core/star/star_handler.py`）

```python
OnEventCompletedEvent = enum.auto()  # 事件处理完成（无论是否被终止），收尾类钩子
```

追加在枚举**末尾**，不改动既有成员的 `enum.auto()` 序号。

### 2. 注册器与对外导出

- `astrbot/core/star/register/star_handler.py`：新增 `register_on_event_completed(priority=0, **kwargs)`，与
  `register_after_message_sent` 同构，仍是 `get_handler_or_create` + `star_handlers_registry.append`。
- `astrbot/core/star/register/__init__.py`、`astrbot/api/event/filter/__init__.py`：导出为
  `filter.on_event_completed`，插件侧直接 `@filter.on_event_completed()`。

### 3. `call_event_hook` 增加 `allow_stopped`（`astrbot/core/pipeline/context_utils.py`）

```python
async def call_event_hook(event, hook_type, *args, allow_stopped: bool = False, **kwargs) -> bool:
```

- 为 False（默认）：完全保持原行为——入口预检、逐处理器终止检查、`notify_event_stopped` 归因，一样不少。
- 为 True：跳过上面两处预检，也不做终止归因（收尾不是终止事件，不该再报「终止传播」），
  某个处理器里 `stop_event()` 也不会中断后续处理器的派发。

关键字专用参数，不占用钩子处理器透传的 `*args / **kwargs`。

### 4. pipeline 收尾派发（`astrbot/core/pipeline/scheduler.py`）

`execute()` 的 `finally` 里：

```python
try:
    if star_handlers_registry.get_handlers_by_event_type(EventType.OnEventCompletedEvent):
        await call_event_hook(event, EventType.OnEventCompletedEvent, allow_stopped=True)
except Exception:
    logger.error(...)
finally:
    event.cleanup_temporary_local_files()
    active_event_registry.unregister(event)
```

三个要点：

- **先探处理器再派发**：没有任何插件注册该钩子时直接跳过。否则每条消息（含未唤醒的）都会走到
  `SessionPluginManager.filter_handlers_by_session` → `sp.get_async` 查一次库，属于纯浪费。
- **异常只记日志**：钩子自身出错不能影响收尾，也不能掩盖 pipeline 原本抛出的异常。
- **内层 `finally` 兜底**：派发期间被 `CancelledError` 打断时，临时文件清理与活跃事件注销仍然执行，不会漏注销。

## 边界与兼容

- 默认 `allow_stopped=False`，既有 12 个钩子的行为、顺序、终止归因全部不变。
- 收尾钩子执行时机在回复阶段之后：`event.get_result()` 已被 `clear_result()` 清空，**不能用 `get_result()` 判断
  有没有回复**，要用 `event._has_send_oper`（`send()` / `send_streaming()` 都会置位）。
- 事件被终止时不会因此多打一条「终止传播」日志：`allow_stopped=True` 的路径不做归因，也不触发 `notify_event_stopped`。
- 会话级禁用插件过滤照常生效（仍走 `filter_handlers_by_session`），被会话规则禁用的插件其收尾钩子也不执行。
- 钩子内可以继续调 `event.send()` 等接口；但此时 pipeline 已结束，发出的消息不参与分段、前缀、T2I 等装饰流程。
- 旧版框架没有这个装饰器，插件需自行降级（`getattr(filter, "on_event_completed", None)`）；「消息回应」v1.2 已按此处理。

## 回归点

- `allow_stopped` 只给收尾类钩子用，其它钩子不得传 True——否则终止传播的短路语义会被破坏。
- 收尾派发必须放在 `cleanup_temporary_local_files()` / `unregister()` **之前**，插件才能看到活跃状态与临时文件。
- 新增检查点仍要遵守 4.27.45 的约定：不得再用「当前 handler」做时序归因。
- 判断「有没有发过消息」统一用 `_has_send_oper`；`get_result()` 在收尾阶段永远是空的。
