# 变更日志 — 2026-11-10 — 插件/钩子/模型/管道异常接入重要通知 + 通知删除 + 壁纸远程取图流式代理

## 背景

两件事同时落地。

**其一**：重要通知此前只有「上下文压缩失败」一个来源，而实际最需要被看见的是**插件报错**——用户在群里发一句话没反应，机器人侧其实抛了 `NameError` / `KeyError`，日志里躺着一整段调用栈，但管理员要翻日志才知道。尤其事件钩子（`on_llm_request`、`on_decorating_result` 等）里的异常被 `except BaseException` 吞掉只打日志，连插件作者都不容易发现。

**其二**：随机壁纸 API 每次请求都换图，而浏览器因为 canvas 污染无法跨域取回图片字节。直接后果是「设置页看到的那张」和「页面背景那张」「点下载得到的那张」是三张不同的图。要保证「存下的 = 看到的」，取图必须由服务端代理一次；而原先的代理是「先收完再吐」，浏览器要等整张图下完才开始绘制，比直连慢 3-4 秒。

## 改动

### 1. 异常统一进通知中心（`astrbot/core/notification.py`）

新增 `build_error_detail()` 与五个入口，覆盖此前所有「只打日志」的异常路径：

| 入口 | 通知 key | 触发位置 |
| --- | --- | --- |
| `notify_plugin_error` | `plugin_error:{插件}` | 插件 handler 抛错（`star_request.py`） |
| `notify_plugin_hook_error` | `plugin_hook_error:{插件}` | 事件钩子抛错（`context_utils.call_event_hook`、`result_decorate/stage.py` 的 `on_decorating_result`） |
| `notify_agent_error` | `agent_error:{runner}:{模型}` | 内部 Agent / LLM 调用失败（`internal.py`）、第三方 runner 失败（`third_party.py`） |
| `notify_pipeline_error` | `pipeline_uncaught:{异常类型}` | 事件总线 `create_task` 未捕获异常（`event_bus.py::_on_task_done`） |
| `notify_plugin_load_error` | `plugin_load_error:{插件}` | 插件载入失败（`star_manager.py`） |

细节：

- 详情统一格式：时间 / 平台 / 群号 / 发送者 / 会话标识（umo）/ 插件与处理函数 / 异常类型与信息 / 调用栈，超长中间截断（`DETAIL_MAX_CHARS=4000`、`TRACEBACK_MAX_CHARS=2800`）。
- 同 key 未读通知聚合：`count + 1`、刷新详情与时间。此前只刷详情不刷标题，插件换了报错位置时标题还停在旧内容，现在一并刷新。
- 钩子异常显式过滤 `CancelledError`，避免正常取消被记成报错。
- 管道异常用 `create_task` 写库（不阻塞主调度），任务句柄集中收集，shutdown 时 `gather`，避免「进程退出时通知没落库」。
- 写入失败只记日志，绝不反向影响业务主流程。

### 2. 通知展示与删除

- `help.py`：聊天里的通知详情从「整段调用栈刷屏」压成**单行 160 字摘要**，完整内容引导到 WebUI 通知中心查看。
- `NotificationCenter.vue`：长详情默认折叠 6 行 + 展开/收起 + 复制详情；展开/复制改为图标按钮，与「标记已读」并到同一行 footer（左时间、右操作）；面板加宽到 560px（`max-width: calc(100vw - 24px)` 防窄屏溢出），列表高度 `min(60vh, 600px)`，字号整体上调。
- 删除能力：`NotificationService.delete_notifications(ids | clear_read)` + `POST /notifications/delete`；前端每条通知加删除按钮，面板头部提供「清空已读」。传 `ids` 删指定条目（不论已读），`clear_read=True` 只删已读、保留未读。

### 3. 壁纸远程取图：流式代理 + 令牌（`dashboard_preference_service.py` / `dashboard_preferences.py`）

`GET /api/v1/ui-preferences/wallpaper/proxy?url=&t=`：

- **带令牌 `t`（新路径）**：命中令牌缓存直接返回字节（`Cache-Control: immutable`，URL 含唯一令牌所以可长缓存）；未命中则 `open_remote_wallpaper_stream()` **边收边转发**（`StreamingResponse`），浏览器边下边画，首屏不再等整张图；读完后把这份字节钉在令牌上。
- **不带 `t`（旧调用）**：一次性收完再返回，兼容既有调用方。
- 令牌缓存 LRU：最多 8 张 / 48MB / 6 小时，超出按最久未用淘汰。
- 安全与健壮性：仅允许 http(s)、跟随重定向但有上限、单张上限 32MB（超限只透传不进缓存）、UA 伪装（不少图源按 UA 拦截）、**按文件头嗅探真实类型**（不少 API 返回 `application/octet-stream` 甚至 `text/html`）、复用共享 `httpx.AsyncClient`（省掉每张图 0.3-1s 的建连与 TLS 开销）、尊重环境变量里的 http(s)_proxy。

### 4. 前端「直连 / 服务端」二选一（`wallpaperImageStore.js` / `wallpaperApplier.js` / `Settings.vue`）

- 背景、设置页预览、下载当前壁纸**共用同一份解析后的地址**（同令牌），因此天然是同一张；「换一张」= 换令牌。
- 新增 `wallpaperUseProxy` 偏好（localStorage，按浏览器保存，不跨设备同步）；**默认值按设备**：手机走服务端（保证同图），电脑走直连（更快，需要原图可自行从 F12 取）。
- 直连模式下预览区不重复拉图（随机图源 `no-store`，再拉必然得到另一张），只显示说明；失败预检也跳过 —— 一次浏览只发一次请求。
- 直连模式的「换一张」依赖 `_n=令牌` 一次性参数才能拿到新图（签名链接不加）。
- 保存壁纸时 `adoptWallpaperDisplay` 把旧令牌认领到新版本号，避免「保存完背景立刻换了一张」。
- 撤销了中途试过的 IndexedDB 持久缓存：随机壁纸的玩法就是刷新换一张，持久化会让刷新永远是同一张。

### 5. 附带：`raw_message` 类型标注

`AstrBotMessage.raw_message` 由 `object` 改为 `Any`，消除下游取值时的类型告警（纯标注改动，无运行时行为变化）。

## 验证

- `ruff check` 通过；改动 Python 文件 `py_compile` 通跑。
- 通知链路用假 handler + 假 event 模拟：插件钩子抛 `NameError` → 通知标题含插件名、详情含钩子名/群号/时间；同级异常再触发一次只 `count + 1`，不新增条目。
- 通知删除：按 id 删除、`clear_read` 清空已读两条路径均返回正确条数，未读条目不受影响。
- 壁纸取图实测：picsum 正常返回且按文件头嗅探出 `image/jpeg`；非图片响应 / 404 / 非 http(s) 地址均给出明确错误；同一令牌二次请求字节完全一致（md5 相同）；未加令牌的随机 API 连续两次取图 md5 不同，验证了「服务端代取 + 令牌」是同一张图的必要条件。
- 流式路径用大图观察首字节时间明显早于整图下载完成。
- 前端 `vue-tsc --noEmit` 与 `vite build` 通过，产物已同步到 `dashboard/dist`。

## 部署 / 测试注意

- 需重启 ldm 生效（通知埋点与壁纸服务均为后端改动）。
- 无数据库迁移：`important_notifications` 表沿用 v4.27.58 的持久化结构，新增的只是写入方与删除接口。
- 通知量与异常频率正相关，同 key 聚合后不会因循环报错刷爆列表；若某插件长期报错，通知会累加 `count` 而不是无限新增。
- 壁纸令牌缓存按进程内存计，重启后首次访问各图会重新回源；对随机图源每次「换一张」都会真正回源一次（这是设计预期）。
- 电脑端默认直连，因此「下载当前壁纸」可能与背景不是同一张（随机图源特性），需要严格一致请在设置页切到「服务端（同图）」；手机端默认已是同图模式。
