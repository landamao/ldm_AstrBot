# 变更日志 — 2026-11-01 — FAISS 文档库生成列迁移修复（启动不再刷 duplicate column）

## 背景

知识库使用 FAISS 向量库时，每次启动都会在日志里刷出一条告警：

```
创建 documents(user_id) 索引失败
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) duplicate column name: kb_doc_id
```

列其实早已存在，迁移本应直接跳过；但每次启动都重跑一遍 ALTER，报错后被外层 `except` 吞成一条 WARNING，功能不受影响却持续污染日志。

## 根因

`DocumentStorage` 初始化时的列判断依赖 `PRAGMA table_info(documents)`：

```python
pragma_result = await conn.execute(text("PRAGMA table_info(documents)"))
existing_columns = {row[1] for row in pragma_result.fetchall()}
if "kb_doc_id" not in existing_columns:
    ... ALTER TABLE documents ADD COLUMN kb_doc_id ...
```

两个问题叠在一起：

1. **`PRAGMA table_info` 不返回生成列（GENERATED）**。`kb_doc_id` / `user_id` 都是 `GENERATED ALWAYS AS (json_extract(metadata, '$.xxx'))` 的虚拟列，于是 `existing_columns` 里永远查不到这两个名字，`not in` 判断恒为真 —— 无论列是否已存在，每次启动都执行一次 ALTER。
2. **原来的新增列用的是 `STORED`**。STORED 生成列需要物化写入，部分 SQLite 版本不支持通过 `ALTER TABLE ADD COLUMN` 添加（只能在建表时声明）；本项目运行环境包含 Android proot 等自带较旧 SQLite 的场景，这条路径在那些机器上即便列不存在也会失败。

主要是第 1 点让迁移永远不幂等，第 2 点是顺带加固：新增列改用各版本都支持的 `VIRTUAL` 形态。

## 改动

`astrbot/core/db/vec_db/faiss_impl/document_storage.py`：

1. **列探测改用 `PRAGMA table_xinfo(documents)`** —— `table_xinfo` 会包含生成列（`table_info` 不含），已有列能被正确识别，迁移真正幂等。
2. **新增列一律用 `VIRTUAL`** —— VIRTUAL 生成列同样可以建索引、查询成本可接受（按需 `json_extract`），且各版本 SQLite 都支持 `ALTER TABLE ADD COLUMN` 添加；STORED 在旧版本不支持。
3. **逐列 `try/except`** —— 两列分开处理，捕获到 `duplicate column name` 时静默跳过（多实例并发初始化、或历史库已由其它路径建好该列），其它异常照常抛出。
4. **日志措辞修正** —— `创建 documents(user_id) 索引失败` → `初始化 documents 生成列/索引失败`，覆盖范围与实际的 try 块一致。

## 修改文件清单

| 文件 | 改动 |
| --- | --- |
| `astrbot/core/db/vec_db/faiss_impl/document_storage.py` | `table_info` → `table_xinfo`；新增列 `STORED` → `VIRTUAL`；逐列 try/except 忽略重复列；异常日志措辞修正 |

## 验证

- `py_compile` 通过。
- 用 Python `sqlite3`（3.53.1）复现两条行为，确认根因与修复方向：
  - `PRAGMA table_info` 对 `GENERATED ALWAYS AS (json_extract(...)) VIRTUAL` 列返回 `['id', 'metadata']`，`PRAGMA table_xinfo` 返回 `['id', 'metadata', 'a', 'kb_doc_id']` —— 证明原判断确实恒为真，是刷日志的直接原因；
  - 重复 `ALTER TABLE ADD COLUMN kb_doc_id` 报 `OperationalError: duplicate column name: kb_doc_id`，与日志里那条告警完全对应；
  - `VIRTUAL` 生成列建索引后按值查询可命中（`SELECT id FROM documents WHERE kb_doc_id = 'kb-9'` → 命中），VIRTUAL 形态不影响本项目的等值查询与索引使用；
  - 另注：本机 3.53.1 上 `ALTER ... STORED` 实际可执行，因此 STORED → VIRTUAL 属于「旧版本兼容 + 不占存储」的加固，不是本次报错的唯一条件。

## 部署 / 测试注意

- 重启生效，无数据库迁移脚本、无需手工处理。
- 存量库里已经建好的 STORED 生成列不会被改动（SQLite 无法原地切换物化方式）；本次只影响「新建库」和「尚未添加该列的旧库」。
- VIRTUAL 列不占存储、读取时计算；本项目对该列只做等值查询与索引，行为与 STORED 一致。
