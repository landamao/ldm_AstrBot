# [2026-09-01] WebChat 重试机制重构：上一条用户消息重发，删除 can_regenerate 全套判定

> 本文件为独立变更日志，记录 2026-09-01 WebChat（ChatUI）重试（regenerate）机制重构：
> 重试改为「复用上一条用户消息重新发送」，彻底删除旧的 /regenerate 接口与
> can_regenerate 判定体系，根治 `Invalid key: message_id`，插件消息也变为可重试。

---

## 问题现象

- 报错（llm_error）的消息点重试直接报 `Invalid key: message_id`；
- 重试按钮时有时无，依赖后端 can_regenerate 权威标志 + checkpoint 是否在
  LLM 历史中判定，插件/指令消息永远不可重试；
- 前端重试时先把 botRecord.id 换成 `local-regenerate-*` 占位符，一旦请求失败
  恢复逻辑出偏差，再次点击就把假 id 传给后端 `int(message_id)` 解析失败；
- 08-30 修过一轮（can_regenerate 下发 + llm_error 分流），08-31 断线续流、
  停止打断等改动又在此链路上叠加，机制越修越复杂、越修越脆。

## 设计思路（全部推倒重来）

重试不再需要专用接口和 checkpoint 定位：

- 前端找到被重试 bot 消息前面最近的一条用户消息，取出其消息内容；
- 像正常发消息一样重新发起请求（走同一条 send SSE/WS 通路）；
- 后端在发送前按传入的用户消息 id 把该轮次清干净；
- 判定逻辑只剩「最后一条 bot + 不在流式中 + 前面有用户消息」，
  llm_error、stopped、插件消息、AI 回复一视同仁，全部可重试。

## 改动内容

### 后端 `astrbot/dashboard/services/chat_service.py`

- 新增模块级 `truncate_turn_from_user_message(...)`（SSE/WS 两条通路共用）：
  - 删除该用户消息之后的所有 platform_message_history 记录
    （bot 回复、报错、插件消息等）；
  - 删除被删记录关联的 webchat threads（含停掉活跃 agent、清理 conv、
    清理队列、删 thread 平台历史）；
  - conversation history 截断：用 `find_turn_range` 定位用户消息 checkpoint
    所在轮次，保留轮次之前的内容；checkpoint 不在历史中（llm_error 轮次/
    插件轮次）则失败轮次本就不在历史，保留整段即可；
  - 用户消息本身不删，换新 checkpoint（重新请求视为全新一轮）；
  - 返回新 checkpoint id；找不到记录返回 None。
- `ChatService._truncate_turn_from_user_message` 薄封装委托模块级函数；
- `build_chat_stream` 支持 `_truncate_from_message_id`：校验会话归属与
  权限 → 执行清理 → 用返回的新 checkpoint 作为本次请求的
  `llm_checkpoint_id`（用户消息落库复用原记录，`_skip_user_history` 不需要）；
- **删除**：
  - `prepare_regenerate_message_payload` 及
    `prepare_regenerate_message_payload_from_dashboard_payload`；
  - `_prepare_llm_error_regenerate`；
  - `_can_regenerate_now` / `_can_regenerate_message` /
    `_is_llm_error_message` / `_has_stopped_part`；
  - `get_session` 不再加载 conversation history 逐条计算 can_regenerate，
    直接序列化返回；
  - `_consume_chat_run` 三个 `message_saved` 发送点的 can_regenerate 字段；
  - stop_session 中过时的 can_regenerate 相关注释。

### 后端 `astrbot/dashboard/services/live_chat_service.py`（WS 通路）

- `t=send` 处理支持 `_truncate_from_message_id`：校验 → 清理 → 用新
  checkpoint 作为本次 `llm_checkpoint_id`；出错时回发 error 帧并终止；
- `message_saved` 下发删除 can_regenerate 字段；
- 删除未使用的 `ChatService` 导入（ruff 提示）。

### 后端 `astrbot/dashboard/api/chat.py` / `schemas.py`

- 删除 `POST /chat/sessions/{session_id}/messages/{message_id}/regenerate`
  路由与 legacy `/api/chat/message/regenerate` 路由；
- 删除 `ChatMessageRegenerateRequest` schema。

### 前端 `dashboard/src/composables/useMessages.ts`

- `regenerateMessage` 重写：
  - 在本地消息列表中找到被重试 bot 前面最近一条用户消息；
  - 本地列表截断到该用户消息（含），追加新的 isLoading bot 占位；
  - 复用用户消息 parts（stripUploadOnlyFields 后）走正常 `sendMessageStream`，
    仅多传 `truncateFromMessageId`（用户消息已落库的真实 id；本地占位
    用户消息不传，后端无需清理）；
  - 不再有 `local-regenerate-*` 假 id 轮换，不再有失败恢复逻辑。
- `SendMessageStreamOptions` / `sendMessageStream` / `startSseStream` /
  `startWebSocketStream` 增加 `truncateFromMessageId` 参数，
  SSE body 与 WS payload 均带 `_truncate_from_message_id`；
- 删除 `ChatRecord.can_regenerate` 字段及 `message_saved` /
  `appendErrorPart` / stopped part 中的相关赋值。

### 前端 `dashboard/src/components/chat/ChatMessageList.vue`

- `canRegenerateMessage` 简化：最后一条 + 非流式中 + 前面存在用户消息
  即可重试（`latestUserIndexBefore`）；删除 llm_error/stopped 特判与
  can_regenerate 标志判断；生图会话保持不变。

### 前端其他

- `dashboard/src/api/v1.ts`：删除 `regenerateMessage`、
  `regenerateMessageUrl` 与 `ChatMessageRegenerateRequest` 导入；
- `dashboard/src/components/chat/ThreadPanel.vue`：`message_saved`
  处理删除 can_regenerate 逻辑。

### 测试

## 部署 / 测试注意

- 后端改动需**手动重启 ldm** 生效；前端刷新（Ctrl+F5）即用新 dist；
- 建议验证：
  1. 发消息触发报错（如 `/llm` 后选不存在的模型）→ 点重试 → 应正常
     重新请求，不再报 `Invalid key: message_id`；
  2. 正常 AI 回复点重试（直接点 + 选模型重试）→ 旧回复被清掉、重新生成；
  3. 插件/指令消息（如 `/help` 输出）→ 重试按钮现在也会显示且可用；
  4. 重试后刷新页面，消息顺序与 LLM 上下文一致，无重复轮次。
