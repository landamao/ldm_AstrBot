# 变更日志：上下文占用快照修复低占用误压缩（2026-09-05）

## 概述

对应上游 issue [AstrBot#9864](https://github.com/AstrBotDevs/AstrBot/issues/9864) 与 PR [#9865](https://github.com/AstrBotDevs/AstrBot/pull/9865) 的本地实现。修复 LLM 长对话（尤其多轮工具调用 + 带 prompt cache 的 provider，如 DeepSeek）中，上下文占用远低于阈值却被提前触发压缩/截断，导致对话"失忆"（搜不到、答不出之前聊过的硬信息，甚至乱编）的问题。

## 背景 / 根因

**现象**：界面环形图显示占用仅 6.8%（54K~97K / 1M 窗口），却触发压缩把 97K 真实上下文压成 19K；有时"回答过程中"就被压缩。报告者实测单轮 usage 合计高达 2.8M~3.8M token。

**根因链**（修复前代码）：

1. `tool_loop_agent_runner.py` 每次拿到最终 LLM 响应后，`conversation.token_usage = usage.total`，而 `total = 非缓存输入 + 缓存命中 + 输出`。缓存命中的 token 是**重复读取历史**，不增加上下文长度，但计费值把它全算进去——issue 数据中 36 次调用累计 cached 22.3M vs 非缓存输入 1.26M，该持久化值被撑到数百万。
2. 下一次 `step()`（含工具循环内每一轮迭代、回答中途）开始时，把这个持久化值原样作为 `trusted_token_usage` 传给 `ContextManager.process()`。
3. `EstimateTokenCounter.count_tokens()` 只要 `trusted_token_usage > 0` 就**完全替代**对真实消息列表的逐条估算。
4. `should_compress()` 判断 `该值 / max_context_tokens > ~0.82` 即压缩：3.8M / 1M ≈ 380% 必然触发。压缩器丢轮最坏情况（非 system 消息 ≤ 2×drop_turns）会**清空全部消息**只回插第一条 user 消息 → 整段失忆。

**界面"健康"与压缩矛盾的原因**：界面读 `stats.current_context_tokens = usage.input`（仅最近一次输入），压缩判断用的是 `usage.total`（含缓存命中 + 输出），两个口径根本不同。

## 改动

`astrbot/core/agent/runners/tool_loop_agent_runner.py`（与上游 PR #9865 同方案）：

- 新增 `_ContextUsageSnapshot` 数据类：`prompt_tokens`（真实 `usage.input`）+ 消息列表逐条 SHA256 指纹 + 工具 schema 指纹 + provider 引用。
- 新增 `_context_usage_fingerprints()`：消息逐条 `model_dump()` 后 sha256；工具集对 active/description/name/parameters 算指纹。
- `reset()`：快照初始化为 `None`。
- `step()` 压缩判断不再读 `conversation.token_usage`，改为：
  - 仅当存在快照、且 `enforce_max_turns == -1`、同一 provider、工具 schema 未变、当前消息是快照消息的**严格前缀扩展**时，`trusted = 快照 prompt_tokens + 新增尾部消息本地估算`；
  - 任一条件不满足（含压缩后历史被改写、hook 原地改消息、schema 变更、fallback 切换 provider）一律 `trusted = 0`，退回本地逐条估算——真实约 97K 的上下文远低于 820K 阈值线，不再误压缩；
  - `process()` 之后若压缩/截断破坏了快照前缀，快照作废；
  - LLM 响应带 usage 且 `input > 0` 时，把当前 `run_context.messages`（此刻恰为发给 provider 的完整 prompt，assistant 回复在其后 `_handle_function_tools` 才追加）与 `usage.input` 绑定写入新快照。
- `conversation.token_usage = usage.total` 的计费口径保留不变（供统计/展示）。

**与上游 PR #9865 的差异**：本地 4.27.21 的 `step()` 没有 `_await_or_stop` 包装与 `process()` 返回 `None` 的中止分支，故该处保持本地原样（直接 `await`），其余逻辑与 PR 一致。

## 测试

`tests/test_context_usage_snapshot.py`（本仓库脚本式风格，`python tests/test_context_usage_snapshot.py`）：

- `test_stale_conversation_token_usage_no_early_compression`：`conversation.token_usage=3,879,963`（issue 第 4 轮实测值）+ 真实约 96K 上下文 → 不压缩，历史回答与当前问题均保留；并保留旧行为对照断言（同值作 trusted 传入会清空整个上下文）。
- `test_tool_loop_reuses_real_prompt_usage_snapshot`：工具循环内第一次 `usage.input=900`（> 820 阈值线，`max_context_tokens=1000`），第二次请求按快照复用占用并加尾部增量，正确触发压缩丢掉最老一轮、当前问题保留。
- `test_reestimates_after_in_place_message_mutation` / `test_reestimates_after_in_place_schema_mutation`：hook 原地改历史消息 / 改工具 schema 后快照指纹不匹配，两轮 `trusted_token_usage` 均为 0。

回归：`tests/test_tool_interrupt_context.py` 全部通过；ruff、`py_compile` 通过。
