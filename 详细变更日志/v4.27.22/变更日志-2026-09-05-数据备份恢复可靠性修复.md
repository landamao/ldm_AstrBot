# 修复：数据备份恢复可靠性（附件可迁移、导入失败回滚、配置文件补全、失败不再静默）

- 日期：2026-09-05
- 背景：全面审计备份/恢复逻辑（`astrbot/core/backup/`）后发现的问题与修复记录。审计结论：
  - **附件不可迁移（最严重）**：`attachments` 表的 `path` 存的是导出机器上的绝对路径。同一安装目录恢复没问题；恢复到不同目录或另一台机器时，附件还原到旧绝对路径，路径越界校验失败后直接跳过，结果**所有附件文件全丢、记录全部指向无效路径**，且无法事后补救。
  - **主库清空后导入失败无回滚**：replace 模式先独立事务清空 13 张表，之后导入失败直接 return，主库停在"已清空 + 部分数据"状态。目录/配置有 `.bak` 兜底，主数据库没有任何备份。
  - **`mcp_server.json`、`skills.json` 未备份**：前者是用户配置的 MCP 服务器列表（`func_tool_manager.py` 读取），后者是 skill 启用/禁用状态，均为用户数据，恢复后丢失。
  - **导出失败静默吞掉**：单表/KB 导出失败只打 warning 并导出空表，备份照样"成功"，manifest 记 0 条，用户无法察觉数据缺失。
  - **checksums 形同虚设**：manifest 里算了 SHA256 但导入端从不校验，ZIP 内文件损坏不会被发现。
  - **目录导入不原子**：旧目录先整体 move 到 `.bak` 再逐文件解压，中途出错留下不完整的新目录。
  - **manifest 缺 `has_knowledge_bases`/`has_config` 字段**：导入确认页的"包含知识库/配置文件"摘要芯片依赖这两个字段，永远不显示。

## 改动

### `astrbot/core/backup/constants.py`

- 新增 `BACKUP_CONFIG_FILES`：`("cmd_config.json", "mcp_server.json", "skills.json")`，导出/导入两端共享。
- `BACKUP_MANIFEST_VERSION` 升到 **1.2**（老备份 1.1/1.0 仍可正常导入，缺失字段自动跳过）。

### `astrbot/core/backup/exporter.py`

- **核心数据导出失败即整个备份失败**：主库单表、KB 元数据表、KB 文档、FAISS 索引导出失败直接 raise（沿用现有"失败清理 ZIP"路径），不再导出空表假装成功。
- **文件级失败记录不静默**：KB 媒体文件、目录内单文件、附件导出失败记入 `self._export_errors`；附件"数据库有记录但文件不存在"也明确记录。清单写入 manifest 新增的 `export_errors` 字段。
- **配置文件补全**：新增 `_export_config_files()`，把 `cmd_config.json`、`mcp_server.json`、`skills.json` 写入 ZIP 的 `config/` 段（带 checksum）。
- manifest 新增 `has_knowledge_bases`、`has_config`、`files.config`、`export_errors` 字段。

### `astrbot/core/backup/importer.py`

- **checksum 真正生效**：新增 `_verify_checksums()`，在**任何写操作（清库、覆盖文件）之前**校验 manifest 中全部 SHA256，失败直接拒绝导入（不清库）。备份无 checksums（老版本）时跳过。
- **清空与导入合并同一事务**：`_clear_main_db` + `_import_main_database` 合并为 `_clear_and_import_main_db()`，清空 13 张表和导入所有行在同一个事务中，任何失败（字段不兼容、约束冲突、进程中断）整体回滚，现有数据保持导入前原样。单行失败仍通过 SAVEPOINT（`session.begin_nested()`）隔离跳过，不拖垮整体。失败提示为「导入主数据库失败（已回滚，现有数据未受影响）」。
- **附件跨环境恢复**：`_import_attachments()` 重写。同一安装目录内恢复按原路径还原、路径不变；备份来自其他安装路径时，附件改写到当前 `data/attachments`（保持原文件名，文件名被占用时改用 `{attachment_id}{ext}`），并同步 `UPDATE attachments SET path`，恢复后附件可访问。原路径无效/记录缺失时回退落到当前附件目录。附件查找改为 id 索引，`src.read()` 换 `shutil.copyfileobj` 流式拷贝。
- **其余配置文件导入**：ZIP `config/` 段中的 `mcp_server.json`、`skills.json` 写回 `data/` 根目录，先备份 `.bak`，逐文件容错。
- **目录导入原子化**：先解压到同级暂存目录 `.{name}.importing`，全部成功后才把旧目录移入 `.bak`、暂存目录就位；解压中途失败删除暂存目录并放弃替换，旧目录原封不动。单文件解压失败仍逐条 warning 不中断。

### `astrbot/dashboard/services/backup_service.py`

- 导出任务完成后读回 manifest，把 `export_errors` 透出到任务结果（`result.warnings`）并打 warning 日志，避免用户拿到缺数据的备份而不自知。

## 两项核查后决定不修

- **导出一致性快照**：核查 `get_db()` 后确认 13 张表的查询实际处于同一 SQLAlchemy autobegin 事务（SQLite WAL 快照读），评估时过于保守，无需改动。
- **导入期间暂停平台写入**：事务化根治后，并发写最多造成"恢复后又产生少量新数据"，不再有损坏风险；而停/起平台适配器若失败会让 bot 掉线，风险大于收益。

## 说明

- `site-packages/`（插件依赖缓存）维持不备份：平台相关、体积大、插件加载时可重装；备份它反而会让跨机器恢复带上不可用的二进制。离线迁移时插件首次加载需联网装依赖。
- 导入完成后仍需**重启**生效（配置文件与插件目录已替换，运行态为旧内存对象），前端 `restartRequired` 提示已有。
- 备份 manifest 从 1.1 升到 1.2；新字段均为增量，旧版 ldmbot 导入新备份不受影响（多余字段被忽略），新版导入旧备份靠"字段缺失即跳过"兼容。
