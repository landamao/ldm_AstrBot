# [2026-10-10] 终止传播日志归因修复：从时序猜测改为停止时留痕

> 本文件为独立变更日志，记录「插件「X」（handler）终止了事件传播」日志归因机制的修复与配套的钩子预检。

---

## 问题现象

终止日志的旧归因方式是**事后时序猜测**：管线在三个检查点（star_request 每个处理器执行后、`call_event_hook` 每个钩子执行后、装饰阶段每个钩子执行后）检查 `event.is_stopped()`，停了就归给"刚执行完的那个"。停止发生时从不留任何信息，于是凡是事件被"别人"终止、而流程恰好恢复在某个处理器之后，锅就落在那个插件头上。加上同一事件去重首报独占，第一个（可能错误的）归因同时占据日志与 WebChat 终止卡片。

三条具体的冤案路径：

1. **会话指令外部终止**（最常见）：`/reset`、`/compact`、`/stop`、`/new`、`/rename`、`/del` 及 `/persona` 切换经 `active_event_registry.stop_all(umo, exclude=自己)` 把同会话所有其它在途事件直接 `stop_event()`。被终止事件的流程稍后恢复，走到最近的检查点，把当时正 await 着的处理器记成终止者。打断机制（`request_agent_stop_all`）不走 `stop_event()`，不在冤案之列。
2. **洋葱模型挂起窗口**：插件 handler `yield` 后，调度器递归执行完所有后续阶段（分段发送每段 sleep 1.5s，窗口可达数秒）才回到该插件。窗口内事件被外部终止，恢复执行完毕后命中 star_request 的后置检查——该插件背锅。
3. **钩子循环无入口预检**：事件在进入钩子循环之前就已死（on_llm_request 前隔着防抖等待、`wait_until_idle` 最长 8 秒、会话锁、构建 agent 一长串 await；on_waiting_llm_request 前隔着防抖与打断收尾），列表里**第一个**钩子处理器被照常执行——代码跑了、副作用真实发生——然后命中后置检查背锅。

另有一个独立痛点：终止日志只有固定格式，无从判断对应哪次事件。

## 用户定案

- 归因必须真实；判断不出来源时输出固定文案「事件被终止传播，未找到调用点。」，**不回退时序猜测**。
- 日志附带消息概要 `event.get_message_outline()`（空消息占位「（空）」）。
- 事件已死不再执行任何钩子处理器。审计类"靠钩子记录所有出站消息"的依赖本就因处理器排序不可靠（下一个执行到的不一定是审计插件），用户确认接受此行为变更。
- 用户插件定式 `stop_event()`（本轮我接管，后续都不执行）+ `yield` 发消息：消息必须照常发出。

## 修复内容

### 1. `stop_event()` 停止时留痕（astr_message_event.py）

首次调用时从 `sys._getframe(1)` 向外走 `f_back` 链，把 `(f_code, f_lineno)` 存入 `event._stopped_by_frames`。**只存 code 对象与行号，frame 对象不入列**——frame 对象会钉住 `f_locals` 与整条 `f_back` 链（调用链上所有局部变量都被钉住无法回收），而 code 对象在函数定义时就产生、被函数对象自身永久引用，持有成本为零。首次停止为准，重复调用不覆盖；`continue_event()` 清除留痕。

### 2. 来源解析（context_utils.py 新增 `resolve_stop_source`）

从 `star_handlers_registry.star_handlers_map` 建立 code 对象 → (插件模块, handler 名) 映射，沿留痕栈由内向外找第一个注册处理器帧。由此：

- 插件直接 `stop_event()` → 正确归到该插件（生成器 handler 运行期间其帧在链上，可命中）。
- `/reset` 等指令经 `stop_all` 外部终止 → 栈内含指令处理器帧，正确归到「builtin_commands」（对应指令名下）。
- 框架阶段、后台任务等非插件来源 → 匹配不到 → 「未找到调用点」。

**必须兼容生产绑定方式（真实环境验证暴露的盲区）**：处理器注册发生在插件类定义期（装饰器拿到裸函数），插件实例化后 `star_manager` 把 `md.handler` 重绑为 `functools.partial(裸函数, 实例)`（LLM 工具同样处理，`agent/tool.py` 的 `handler_module_path` 注释明说"the handler will be wrapped in functools.partial during initialization"）。`functools.partial` 对象**没有 `__code__`**，直接 `getattr` 取不到——首版解析器因此把所有插件类处理器跳过出匹配表，表现为用户插件 `stop_event()` 也一律"未找到调用点"。修复：`_handler_code` 循环拆 `partial.func` 到最底层函数再取 code（同时保留 bound method 走 `__func__` 的分支），partial 绑定后的钩子（直接 await）与异步生成器处理器（经 `call_handler` 洋葱机制恢复执行）均验证命中。

### 3. 文案与卡片（context_utils.py）

- 已知来源：`插件「xxx」（handler）终止了事件传播。消息概要「yyy」`。
- 未知来源：`事件被终止传播，未找到调用点。消息概要「yyy」`。
- `notify_event_stopped` 改为单参数，内部自行解析来源；三个调用点（star_request、call_event_hook、装饰阶段）统一。同一事件去重机制保留。
- WebChat 卡片结构不变；未知来源时 plugin/method 传空串，落库端 `str(payload.get(...) or "")` 与前端（只渲染 text）均兼容，无需重建 WebUI。

### 4. 钩子入口预检（context_utils.py、result_decorate/stage.py）

`call_event_hook` 与装饰阶段 process 入口新增 `is_stopped()` 预检：事件已死则补一条真实来源的终止日志后直接返回，不执行任何钩子处理器。与指令链路 star_request 既有预检对齐。

### 5. 有意不做的部分

result 级停止（`set_result_type(EventResultType.STOP)`、构造参数直接传 STOP）不经过 `event.stop_event()`，无留痕 → 归未知文案。不为 dataclass 字段做 property 拦截去追全量留痕——收益边际递减，"未找到调用点"的诚实输出可接受。

## 兼容性

- **`stop_event()` + `yield` 发消息模式逐步验证不受影响**：调度器在停止后的 yield 上 `break` 只跳出洋葱递归，外层阶段循环仍推进到装饰/回复阶段；回复阶段 `_should_stop_sending` 明确不看 `is_stopped()`，已 yield 的结果照常发出。
- **行为变化**：已死事件不再执行任何钩子处理器（含 OnAfterMessageSentEvent）。

## 回归点

- `notify_event_stopped` 统一单参、内部按留痕解析。后续新增检查点时**不得**再往调用方传"当前 handler"做时序归因。
- **涉及注册表的测试桩必须模拟生产绑定方式**：handler 用 `functools.partial(裸函数, 实例)` 构造，不能只注入裸函数——首版测试正是因注入裸函数而漏掉 partial 盲区。
- **`md.handler` 的 partial 绑定是 `star_manager` 的既有机制**：后续在别处按 `__code__`/`__module__` 识别插件处理器时，都必须先拆 partial（`agent/tool.py` 已因同一原因专门保留 `handler_module_path` 字段）。
- 回复阶段不看 `is_stopped()` 的设计（`_should_stop_sending`）是用户插件 `stop_event()` + yield 模式的依赖，别动。
- 留痕刻意不存 frame 对象（内存钉住问题）；若将来要更详细的未知来源信息（如文件:行号），只能从现有 code 对象反查，别改成存 frame。
