# 变更日志 — 2026-11-12 — 恢复备份不再留 .bak，改为恢复前先整包备份

## 背景

备份恢复的兜底方式一直是「把现有目录改名成 `.bak` 留在 data 里」。实测与用户反馈暴露出四个问题：

- **`.bak` 会堆积，且只有一代**：每次恢复都 `rmtree` 掉旧 `.bak` 再生成新的，`data/` 下长期躺着 `plugins.bak` / `plugin_data.bak` / `config` 下的 `.bak`；而上一代的原始数据每次都被静默销毁 —— 既占空间，又没有「多代可回溯」的价值。
- **Windows 上会掏空现有目录（最严重）**：旧实现用 `shutil.move(target → target.bak)`。`shutil.move` 在 `os.rename` 失败（目录内有文件被占用）后会**退化成 `copytree` + `rmtree(src)`**：拷贝能成功（被占用的文件可以被读取），随后 `rmtree` 在锁文件上报 `WinError 32`，此时**目录里除锁文件外的内容已经被删掉了**。
  实测：`config.json / main.py / native.pyd / sub/helper.py` 四个文件，只有 `native.pyd` 被占用；失败后 `plugins/` 里**只剩 `native.pyd`**，`.bak` 里倒是有完整一份，但用户完全不知道。
- **原地重试会二次破坏**：上一步留下的 `.bak` 是普通拷贝、不带锁，第二次恢复时 `rmtree(.bak)` 能成功 —— 上一代数据被删，然后 `copytree` 只拷到残留的锁文件，`.bak` 也跟着降级。两次之后两边都是废的。
- **配置文件也在产 `.bak`**：`cmd_config.json` / `mcp_server.json` / `skills.json` 导入前各 `copy2` 一份 `.bak`，同样无人清理。

结论是换掉兜底模型，而不是把 `.bak` 做得更稳：**恢复前主动导出一份完整备份，恢复时只做原子替换**。

## 改动

### 1. 目录替换改为纯原子改名（`astrbot/core/backup/importer.py`）

`_import_directories()` 的替换流程重写，不再产生任何 `.bak`：

1. 备份内容先完整解压到同级暂存目录 `data/.<name>.importing`；
2. `os.rename(target → data/.<name>.old-<YYYYmmdd_HHMMSS>)` 把现有目录原子移开；
3. `os.rename(staging → target)` 让新目录就位；
4. 成功后立刻 `rmtree` 第 2 步的中转目录。

- **必须避开 `shutil.move`**：`os.rename` 是原子操作，失败时源目录原封不动；`shutil.move` 会回退成 copytree + rmtree，正是上面「掏空」的根因。代码里留了注释，避免以后被“优化”回去。
- **失败即回滚**：若第 3 步失败且第 2 步已改名成功，把 `.old-*` 改回原名；回滚也失败时，错误消息直接给出旧数据的完整路径，不假装成功。
- **中转目录删不掉不改变恢复结论**：`rmtree` 失败只记 warning（附可手动删除的路径），此时新目录已就位。按 Windows 语义，rename 能成功说明当时没有句柄，这一步几乎不会失败。
- 新增 `_atomic_write_bytes()`：配置文件改为「同目录写 `.restoring.tmp` + `os.replace` + fsync」，要么旧内容、要么完整新内容，不再需要 `.bak` 兜底。

### 2. 恢复前整包备份（`exporter.py` / `constants.py` / `backup_service.py` / `schemas.py`）

- 新增 `create_pre_restore_backup()`：封装「按当前进程真实 db / config 导出一份 `*_pre-restore.zip`」，WebUI 服务层与终端共用。
- `export_all()` 新增 `include_knowledge_base_dir`；`get_backup_directories(include_knowledge_base=False)` 增加同名开关，并新增 `get_restorable_directories()` 给导入端识别全部目录类型（导入端只处理 manifest 里列出的目录，旧备份行为不变）。
- `BackupService.import_backup()` 新增 `backup_first`（默认 **True**）：先导出当前数据再恢复；**前置备份失败直接中止**，不动任何数据。恢复是破坏性操作，没有兜底就不该开始。
- 恢复结果新增 `pre_restore_backup`（文件名 / 路径 / 大小），供前端展示与「立即还原」。
- `schemas.BackupImportRequest` 新增 `backup_first: bool | None`；`model_dump(exclude_none=True)` 下缺省即 True，老前端不带该字段时仍是「先备份」。

### 3. 恢复与导出互斥（`backup_service.py`）

两者共用同一份 `.importing` 暂存目录，且恢复期间导出会拍下「一半旧一半新」的脏快照。`import_backup` 与 `export_backup` 统一改为「已有 import/export 任务在跑就拒绝」。

### 4. 终端新增 `--backup`，`--restore-backup` 同步改造（`main.py`）

- `--backup` / `--备份 [输出目录]`：**不启动服务**直接把当前 data 打包，产物与 WebUI 同格式，可用 `--restore-backup` 恢复。这个入口是为「程序起不来 / WebUI 打不开」准备的 —— 那种时候恰恰最需要把数据留底。
  - 全新安装（数据库文件不存在）时先 `db_helper.initialize()` 建表，否则空库没有可导出的表；已有数据库一律不动，避免在事故现场改结构。
  - 终端没有 `kb_manager`，读不了知识库向量库，因此 CLI 备份走 `include_knowledge_base=True`，把整个 `knowledge_base` 目录按原始文件打进 `directories/knowledge_base/**`，恢复时走同一套目录替换。WebUI 备份仍走结构化 KB 导出，不重复占空间。
- `--restore-backup`：新增「恢复前先备份当前数据？[Y/n]」（默认备份，选 n 需二次确认），恢复后逐目录打印结果，任何失败 `exit 1`。
- 两个参数都加入启动横幅跳过列表。

## 验证

- `tests/test_backup_roundtrip.py` 新增 2 个回归用例：
  - `test_directory_import_leaves_no_bak`：恢复成功后 data 目录下不得出现 `.bak` / `.old-*` / `.importing` / `.restoring.tmp`；
  - `test_directory_import_failure_keeps_existing_data`：monkeypatch `os.rename` 抛 `WinError 5`，断言 `success=False`、目录内两个文件都还在且内容仍是恢复前的、无中转残留（旧实现这条会失败）。
- `pytest tests/test_backup_roundtrip.py tests/test_backup_upload_limits.py` → **24 passed**；`pytest -k "backup or import_backup"` → **32 passed**。
- 端到端实测（临时 data 目录）：
  - `--backup` 生成 ZIP，manifest 的 `directories` 只列实际存在的目录；实测覆盖了 `plugins / plugin_data / config / t2i_templates / knowledge_base` 五类；
  - `--restore-backup` 完整替换（备份里没有的 `new_file.py` 随替换消失，不是合并），`data/` 下无任何 `.bak` / `.old-` / `.importing` 残留；
  - 含知识库的备份恢复后 4 个 KB 文件（`kb.db` / `doc.db` / `index.faiss` / `medias/a.png`）完整还原。
- 占用场景实测：目标目录内文件被另一进程持有 → `WinError 5`、退出码 1、目录内三个文件全部保留且内容未变。

## 说明

- **历史遗留的 `*.bak` 没有自动清理**：属于用户数据，代码不主动删除；需要清理时人工确认后再删。
- **行为变化**：恢复不再提供「自动保留上一份数据」的隐含副本，兜底完全依赖「恢复前备份」。WebUI 默认开启且需显式取消，CLI 默认 Y。
- 恢复仍建议停服务进行：在线替换 `plugins` / `plugin_data` 即使成功，也会让正在运行的插件拿着旧路径（实测出现过插件读不到自己 `data.json` 的情况）。
