# 变更日志 — 2026-11-25 — 群聊上下文增强支持群黑白名单

## 背景

群聊上下文增强（`group_icl_enable`）只有整体开关，一开就全群生效。之前只有
「自动理解图片」带了 `image_caption_group_list`，想让机器人在部分群不记录上下文
只能关掉整个功能。

## 改动

### 1. 新增配置 `provider_ltm_settings.group_icl_group_list`

- 默认 `[]`，空表示不限制群，行为与改动前一致。
- 规则与图片转述的群黑白名单完全一致：直接写群号为白名单、`/` 开头为黑名单、
  `all` / `*` 为全部。示例：`all` + `/123456` 表示除 123456 外都记录；
  仅 `111`、`222` 表示只在这两个群记录。
- 群号与会话 ID（UMO）任一命中即通过，兼容两种填写习惯。

### 2. 生效位置

- `group_chat_context.py::handle_message`：未通过的群不记录消息，也不再触发图片转述。
- `group_chat_context.py::on_req_llm`：未通过的群不注入历史，且**不消费**已积累的
  缓冲——临时把群移出白名单再改回来，之前的历史还在。
- 仅影响群聊上下文增强；主动回复（`active_reply`）仍走自己的 `whitelist`，互不干扰。

### 3. 顺带修复：`all + /群号` 黑白名单组合失效

原判定用 `检测(群号) or 检测(会话ID)`，两个标识分别检测后再取或。白名单含 `all`
时会被规范化成通配符 `*`，此时只要另一个标识没进黑名单，整体就被放行——导致
`all + /123456` 里的 123456 照样生效。

新增 `_群列表放行()` 统一处理：黑名单优先（群号、会话 ID、`/all` 任一命中即拒绝），
再判白名单（含通配符）。图片转述也改走该函数，两处行为一致。

### 4. 其他

- `default.py`：默认值、类型 schema、可视化配置 schema 三处同步，WebUI 配置项
  「群聊上下文群黑白名单」位于「最大消息数量」下方。
- WebUI i18n 同步新增文案并重新构建 `dashboard/dist`。
- 黑白名单解析加了小缓存（最多 32 组），避免逐条消息重复解析。

## 验证

新增 `tests/test_group_context_acl.py`，3 组用例全过：

| 用例 | 断言 |
|---|---|
| 规则 | 空列表 / `all` / `*` / `all+/111` / 白名单命中与未命中 / UMO 命中 / `/all` / 纯空白项 |
| 记录 | 白名单群记录 1 条；白名单外与 `all+/111` 群 0 条 |
| 注入 | 放行群注入 1 条历史；拦截群不注入且缓冲条数不变 |

回归：`tests/test_bare_wake_prompt.py`、`tests/test_leading_content_parts.py` 共
29 条用例通过，`ruff check` 无告警。

## 行为变化

- 配置留空时行为完全不变。
- 若旧配置用了 `all + /群号`，修复后该群会真正被排除（此前是失效的）。
