# 变更日志 — 2026-11-15 — 修复 QQ 语音尾部结束标记导致的 SILK 解码崩溃

## 背景

QQ NT 客户端发出的语音（`nt_data/Ptt/*.amr`，实际是 SILK 封装）在帧流末尾
带一个 `FF FF` 结束标记。这个标记不是一个合法的帧：

- `pysilk` 把它读成帧长 `-1`；
- `BytesIO.read(-1)` 的语义是「读到结尾」，于是把剩余全部数据当成一帧交给 SDK；
- SDK 收到负长度后返回 `-11`（`DEC_PAYLOAD_TOO_LARGE`，名字有误导，实际是长度字段成了负数）。

结果是**整条语音解码失败**，且异常一路冒到调度层，把同一条消息里其它组件
（文本、图片）的处理也一起带崩。截断帧、中间坏帧、头部偏移的包会命中同一条路径。

## 改动

### 1. `astrbot/core/utils/tencent_record_helper.py`：解码前先按帧清洗

- 新增 `_split_silk_frames()`：逐帧读 2 字节长度头，只放行
  `0 < len <= 1024`（`MAX_ARITHM_BYTES`）且数据完整的帧；遇到第一个非法帧即停止，
  因为长度字段一坏，后面的边界就不可信。返回值带上被丢弃的字节数与有效帧数。
- 新增 `_resync_silk_frames()`：严格解析一帧都解不出时，在前 64 字节内滑动尝试，
  取帧数最多的偏移重同步，应对头部多/少字节导致的错位。
- `tencent_silk_to_wav()`：
  - 不再只处理开头的 `0x02` 标记，改为 `find(b"#!SILK_V3")` 定位魔数，
    前面有多余字节也能恢复；
  - 清洗后再拼回完整流交给 `pysilk.decode`；
  - 整体解码失败时退化为 `_decode_silk_frame_by_frame()` 逐帧解码，
    坏帧填 20ms 静音，一帧损坏不再连坐整段语音（上限 3000 帧，约 60 秒，
    防病态文件卡住流水线）；
  - 丢弃字节、重同步、退化逐帧都会打一条 warning，便于定位坏包；
  - 无有效帧或解出空音频时明确抛 `ValueError`，不再抛含糊的 SDK 错误码。

### 2. `astrbot/core/pipeline/preprocess_stage/stage.py`：媒体转码异常就地兜底

- 主消息与引用链两处 `Record` 处理，原先是「`convert_to_file_path` 单独 try +
  `ensure_wav` 另一个 try」，下载阶段的非大小类异常会直接冒到调度层。
  现合并为统一 `try/except`：`DownloadFileSizeLimitError` 仍走「跳过处理」，
  其余异常统一 `Voice processing failed` 告警并继续后续组件。
- 效果：一条语音坏掉只丢这一条语音，不再打挂整条消息。

## 验证

- 用线上报错的那条真实语音（3225 字节，尾部 `FF FF`）复现原错误，
  修复后正常解出 1.14 秒音频。
- 另跑 11 组样本全部符合预期：正常包、尾部截断、中间坏帧、头部偏移、
  非 SILK、空文件、仅头部、尾部 `FF FF`、多组混合坏帧等。
- `ruff check` 无告警。

## 行为变化

- 正常语音解码结果不变。
- 尾部带 `FF FF` 的 QQ NT 语音从「必然失败」变为「正常解码」。
- 单个坏帧不再导致整段音频丢失，会以静音替代并在日志中告警。
- 语音处理失败不再影响同一条消息中的其它内容。
