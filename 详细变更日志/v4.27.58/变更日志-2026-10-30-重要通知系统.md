# 变更日志 — 2026-10-30 — 重要通知系统（压缩失败不再只进日志）

## 背景

上下文压缩失败这类严重问题原来只写日志：日志滚动刷掉或没人主动看，管理员就毫无察觉；而压缩持续失败意味着每次请求都在裸奔（超窗风险），问题会一直潜伏。需要一个**持久化、必达、必须显式确认**的通知机制：

- 通知像日志一样"滚过去就没了"不行——**未读通知必须一直残留**，直到管理员处理；
- 已读必须**手动点击**确认——打开面板/登录都不能算已读；
- 管理员在平台侧发 `help` 指令时，通知要在**输出开头**直接可见；
- WebUI 提供通知中心与未读徽标。

## 改动

### 1. 存储（`astrbot/core/db/po.py`）

新增表 `important_notifications`（SQLModel，`create_all` 自动建表，无需迁移）：

| 字段 | 说明 |
|---|---|
| `key` | 聚合键（如 `context_compress_failed`），索引 |
| `title` / `detail` | 标题与详情 |
| `count` | 同一未读通知的累计发生次数 |
| `read` / `read_at` | 已读标记与时间 |
| `created_at` / `updated_at` | TimestampMixin |

聚合语义：**同一 key 存在未读通知时不再新建**，而是 `count + 1` 并刷新详情与 `updated_at`（避免持续失败每请求一条把通知刷爆）；**已读后同一 key 再次发生 → 生成新通知**（旧问题已确认过，新发生是新提醒）。

### 2. 服务（`astrbot/core/notification.py`，新文件）

`NotificationService` + 模块级单例 `notification_service`：

- `notify(key, title, detail)`：写通知（带聚合）；**任何失败只记 error 日志，绝不影响调用方主流程**；
- `list_notifications(include_read, limit)`：未读在前、按更新时间倒序；
- `unread_count()`；
- `mark_read(ids)`：显式置已读（`read_at=now`），返回实际标记数。

直接使用 `db_helper.get_db()`，不改动 `BaseDatabase` 抽象接口。

### 3. 接入点（`agent/context/manager.py` + `compressor.py`）

上下文压缩失败的两类情况写通知（与上下文管理重构同批落地）：

- 无可用压缩模型：key=`context_compress_no_provider`；
- 压缩无效果/失败：key=`context_compress_failed`，detail 携带触发原因（`check_limits` 的 reason）与压缩器 `last_error`（调用模型失败的具体报错 / 空摘要）。

通知文案中包含「本次请求已按原上下文发送、历史未丢失」与排查指引（检查压缩模型、调整配置）。

### 4. Dashboard API（`astrbot/dashboard/api/notifications.py`，新文件）

- `GET /api/v1/notifications?include_read=&limit=`：通知列表（未读在前）+ 未读数；
- `POST /api/v1/notifications/read`：`{"ids": [...]}` 置已读，返回 `{"marked", "unread"}`；
- 两个端点均 `Depends(require_dashboard_user)` 登录鉴权；响应走统一 `ok()` 封装；
- `router.py` 注册进 API v1。

### 5. help 指令（`builtin_commands/commands/help.py`）

- 新增 `_build_important_notifications()`：取未读通知（最多 20 条），渲染为「⚠️ 重要通知」清单（序号 + 标题 + 「已发生 N 次」+ 详情缩进）；
- `help()` 中**仅当 `event.is_admin()`** 时把清单插到输出最开头（其余版本信息、指令清单不变）；通知在这里**只读展示**，置已读仍需到 WebUI 操作。

### 6. WebUI 通知中心（前端）

- 新组件 `src/components/shared/NotificationCenter.vue`：
  - 顶栏铃铛按钮（`mdi-bell-outline`）+ `v-badge` 红色未读数徽标（>99 显示 99+）；
  - `v-menu` 弹出面板：通知卡片（标题 / 次数 chip / 详情 / 时间），未读高亮左侧边条，已读降透明度并显示"已读"；每条未读有独立「标记已读」按钮（单条调用，loading 态）；
  - **打开面板只负责拉取展示，绝不自动置已读**；
  - 未读数 60 秒轮询 + 打开面板即时刷新；
  - 空状态「暂无重要通知」；铃铛与相邻按钮留 8px 间距（`mr-2`）。
- 挂载点：`layouts/full/vertical-header/VerticalHeader.vue` 的 `header-actions` 区，位于 Bot/Chat 模式切换按钮之前，Bot/Chat 两种模式顶栏均显示。
- i18n：`src/i18n/locales/zh-CN/core/header.json` 新增 `notifications` 节（title/unread/markRead/read/empty）。

## 边界与兼容

- 首次启动自动建表；无任何配置项。
- 通知写入路径全兜底：DB 异常只记日志，不影响 LLM 请求主流程。
- WebUI 通知接口有登录鉴权，未登录 401；平台 help 仅管理员可见通知（`event.is_admin()`）。
- 已读语义 = 「该问题已处理」或「无需处理、我已知道」；未读残留是**有意设计**（持续失败 count 持续累加，逼你看）。

## 验证

- 通知服务用临时 sqlite 库（`SQLiteDatabase(tmp).initialize()` 后替换模块引用）跑全场景：同 key 聚合计数、detail 刷新、mark_read 后未读数下降、**已读后同 key 再发生生成新通知（count 重置为 1）**，全过。
- 导入链冒烟：`notification_service`、`ContextManager`、`dashboard/api/notifications.router`、`build_api_router` 挂载正常。
- `vue-tsc --noEmit` + `vite build` 通过；产物校验：铃铛图标与通知 API 调用进入 `FullLayout-*.js`，文案进入语言包。

### 实机踩坑记录（重要）

首版前端构建后实机验证，用户控制台出现 `SyntaxError: 27`，铃铛组件子树不渲染（页面其余正常）。定位过程：

- `SyntaxError: 27` 的 "27" 是**错误码不是消息**——vue-i18n 错误构造为 `new SyntaxError(String(code))`，27 = `NOT_INSTALLED`；
- 根因：NotificationCenter 误写 `import { useI18n } from "vue-i18n"`（官方库），而**本项目 i18n 是自研的 `@/i18n/composables`**（纯函数、无插件上下文依赖），官方库的 `useI18n()` 检查 `app.__VUE_I18N_SYMBOL__` 不存在即抛 27；
- 修复：改 `import { useI18n } from "@/i18n/composables"`；修复后 vue-i18n 库彻底从构建产物消失（grep `NOT_INSTALLED` 为空）。
- **教训：本项目组件的 i18n 一律 `import { useI18n } from "@/i18n/composables"`；minified 产物里 `SyntaxError: 数字` 先查错误码表再定位。**

## 回归点

- **回归一**：让压缩失败（如把压缩模型 ID 改成不存在的）→ WebUI 铃铛出未读徽标、面板可见通知、help 指令开头出现清单；持续失败只累计 count 不刷屏；点已读后再次失败重新提醒。
- **回归二**：正常压缩成功不产生任何通知。
- **回归三**：普通用户发 help 不出现通知清单（管理员可见）。
- **回归四**：通知面板打开/关闭不产生任何已读标记（网络面板确认无 `/notifications/read` 请求），仅点击按钮时调用。
