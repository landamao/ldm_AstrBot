# 变更日志 — 2026-11-12 — 插件覆盖安装复用同一份包（确认框显示的版本 = 实际装上的包）

## 背景

覆盖安装天然是两次请求：第一次「先看要装的是什么版本」，前端据此弹确认框；用户点确认，第二次「真的装」。改造前这两次各自去取包，代价和隐患都不小：

- **链接 / 直链 / git 安装**：第一次为了读版本，先把完整包下载到本地、解压、读 `metadata.yaml`，抛冲突后把包删掉；用户确认后再按原地址完整下载一遍。加上安装前的仓库预览/预校验，一次覆盖安装前后**完整下载 3 次，其中 2 次纯浪费**。
- **上传安装**：确认后前端要把同一个 zip **重新上传一遍**。
- **更要紧的是正确性**：第二次重新按 URL 取包时，远端 HEAD 可能已经变了（作者刚推了新提交、刚发了新版本），于是出现「确认框写着 4.1.0，实际装上 4.2.0」—— 用户是在不知情的前提下批准了另一个包。上传场景则可能出现「确认的是 A 包，装的是重传时选错的 B 包」。

本次改造的核心是：**把「确认时看到的那份字节」本身留下来，确认后原地复用**，而不是再取一次。

## 改动

### 1. 新增安装包缓存（`astrbot/core/star/plugin_install_cache.py`）

按内容寻址，token 就是包的 sha256（64 位小写 hex），落在临时目录 `plugin-install-cache/<sha256>.zip`：

- `store_archive(zip_path)`：算哈希 → 移入缓存 → 返回 token；同内容的并发副本直接丢弃本次副本（缓存里已有同一份字节）。
- `resolve_archive(token)`：先做 token 白名单校验（64 位 hex，天然挡住路径穿越），再**重算 sha256** 与文件名比对 —— 文件被替换或损坏时校验失败，丢弃并返回 `None`，由调用方回退重新获取。
- `release_archive(token)`：删除缓存包并顺手清掉空目录；token 非法或文件已不存在时静默返回，可安全重复调用。
- `purge_expired()`：24 小时 TTL，最多每 10 分钟触发一次清理（`_last_purge_at` 节流），缓存随系统临时目录自然过期。
- 目录权限 `0o700`。

哈希既是标识也是完整性校验，因此「确认 → 安装」之间不存在被换包的窗口：换掉文件就必须同时改 token，而 token 由前端持有、后端取包时会重算。

### 2. 冲突时先把待装包抓到缓存（`astrbot/core/star/updator.py`）

- `PluginAlreadyExistsError` 从 `star_manager` 迁到 `updator`（`star_manager` 仍重新导出，dashboard 层导入路径不变），新增 `cache_token` 字段。
- 新增 `_stage_pending_archive`：目标目录已存在时按来源取包 —— 有 `download_url` 走直链下载、`git` 传输走浅克隆后 `shutil.make_archive`、其余走 archive 下载；然后用 `inspect_plugin_archive` **直接读 zip 内 `metadata.yaml`** 拿「待安装版本」（不再解压整包），再 `store_archive` 入缓存。
- 取包或写缓存失败**不阻断覆盖确认**：token 置空，退回「确认后重新获取」的旧行为，只是这一轮拿不到「同包」保证，日志会写明原因。
- `install(..., cache_token="")`：token 命中 → 直接 `unzip_file(..., remove_archive=False)` 解压缓存包安装，**不再访问网络**；校验失败则记 warning 并回退重新获取。命中时若目标目录仍在（状态异常），不擅自删已有插件，继续抛冲突交上层确认。
- `unzip_file(..., remove_archive=True)` 与 `_finalize_extracted_archive(..., remove_archive=True)` 新增开关：覆盖确认流程解压后保留压缩包，普通安装行为不变。

### 3. 缓存生命周期（`astrbot/core/star/star_manager.py`）

- `install_plugin` / `install_plugin_from_file` 增加 `cache_token` 参数；`_handle_existing_target` 把 token 透传进异常。
- **成功** → `release_archive`；**非冲突异常** → 也释放（不再需要）；**冲突分支保留**（用户确认后还要复用）。
- 上传安装解压时 `remove_archive=False`，压缩包统一由 `release_archive` 回收，不和确认流程抢同一份文件；未带 token 的老路径仍按临时文件 remove。

### 4. dashboard 接口与前端

- `PluginInstallRequest` 新增 `cache_token`；`PluginSourceBindRequest` 新增 `repo`（见第 5 节）。
- 仓库安装、URL 安装、上传安装三个入口全部透传 `cache_token`；上传接口的 `file` 变为**可选** —— 覆盖确认时只发 token，不再重传 zip。
- `install_plugin_upload`：token 命中直接用缓存包；token 失效**显式报错**（「安装包缓存已失效，请重新选择压缩包后再试。」），不静默改走重新上传/下载 —— 否则又会装到另一份包上，重新引入「版本不一致」。首次上传则先 `store_archive` 再解压。
- 前端 `overwriteConfirmDialog.cacheToken`：从后端 `install_cache_token` 取值；确认时上传只发 `cache_token`，链接安装 payload 带 `cache_token` 并跳过重复预校验；**取消 / 成功 / 关闭弹窗都清 token**，避免「取消后再装」误用上一份旧包。

### 5. 顺带：更换插件源支持自定义 GitHub 仓库

- 后端：`install_method` 为 `github` / `repo` 时可用 `repo` 覆盖插件原有仓库地址，必须能解析成 GitHub HTTP(S) archive 仓库，否则提示「请输入有效的 GitHub 仓库链接。」；未填时仍用插件自带 `repo`（真正没有地址时才报「当前插件缺少仓库地址」）。
- 前端：更换插件源对话框新增「自定义仓库地址」输入，作为**虚拟候选**参与选中（不进入市场候选列表的增删），400ms 防抖调用 `/plugins/validate/repo` 做远端元数据预校验，结果只作提示、不阻止确认；插件无可用仓库时直接展开输入框，避免无从下手。
- `parse_github_url` 与前端 `isGithubRepoUrl` 放宽：分支名允许包含 `/`（`/tree/fix/xxx`）与 URL 编码的 `%2F`，解析后 `unquote` 还原为原始分支名，供 raw 文件与 archive 下载链接使用。

## 验证

- 7 个改动 Python 文件 `py_compile` 全部通过。
- 新增行为逐条实测（本地临时目录，无需网络）：
  - `store_archive` 返回 64 位 sha256，包被移入缓存；同内容第二次 store 返回同一 token 并丢弃副本；
  - 篡改缓存文件后 `resolve_archive` 返回 `None` 且删除被替换文件（日志「插件安装缓存校验失败（内容已变化）」）；
  - `resolve_archive("../../etc/passwd")` / 非 hex 的 64 位串均返回 `None`；`release_archive` 可重复调用；
  - 手动把 mtime 调早 25 小时后 `purge_expired()` 恰好清理 1 个过期包；
  - 构造合法插件 zip 入缓存后调用 `updator.install(repo_url, cache_token=...)`：直接解压到插件目录、`metadata.yaml` 版本为包内 1.2.3、`main.py` 就位、**解压后缓存包仍在**（日志「复用覆盖确认时的插件包安装」），全程未联网；
  - `parse_github_url` 对 `/tree/fix/x` 与 `/tree/fix%2Fx` 均解析出分支 `fix/x`，裸仓库返回分支 `None`。
