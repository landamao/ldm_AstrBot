# 变更日志 — 2026-11-12 — 源码打包脚本误带本机 `.env` 修复

## 背景

`scripts/打包源码.bat`（第 90 行附近）与 `scripts/复制源码.bat`（第 56 行附近）的「复制文件」列表里写的是 **`.env`**，而不是模板 `.env.example`。

后果有两层：

- 眼下就会泄露本机环境：`LDMBOT_DISABLE_UPDATE` / `DASHBOARD_PORT` / `NO_BANNER` / `SET_TITLE` 这类只对作者本机成立的配置，会被当成「出厂默认值」发给别人，导致对方解压后行为与自己本机一致、却与文档描述不符，排查时极难想到是打包带出来的。
- 更大的隐患：`.env` 正是用户填 API Key、数据库密码、面板口令的地方。只要哪天往里面填了密钥，每一次打包源码都会**静默**把密钥打进压缩包发出去 —— 没有任何提示，也不会有报错。

## 改动

- 两个脚本的复制列表统一由 `.env` 改为 **`.env.example`**。该模板一直随版本维护，字段齐全、值全部为空/占位，正好是「给别人看的样板」。
- 复制逻辑本身不变（`if exist` 才复制，缺失则打印「跳过」），因此不影响没有 `.env` 的干净环境。

## 核查

- `runtime_bootstrap.py` 不依赖 `.env` 必须存在：没有该文件时走内置默认值 + 环境变量，首次启动正常。换掉后不影响一键启动。
- `.gitignore` 第 2 行本就忽略 `.env`，所以这次是「打包脚本」层面的漏洞，仓库历史里没有提交过本机 `.env`。

## 修改文件清单

| 文件 | 改动 |
| --- | --- |
| `scripts/打包源码.bat` | 复制列表 `.env` → `.env.example` |
| `scripts/复制源码.bat` | 复制列表 `.env` → `.env.example` |

## 验证

- 逐行核对两个脚本的 `for %%f in (...)` 列表，确认已无裸 `.env` 项。
- 按脚本语义核对分支：源目录存在 `.env.example` 时复制该模板；不存在时走 `else` 打印「跳过 源不存在: .env.example」；两条路径都不会再触碰 `.env`。
