# [2026-10-15] 会话指令与运行中 Agent 的交互治理（/reset 强停清空、/new 与 /switch 运行中拒绝）

> 本文件为独立变更日志，记录 `/reset`、`/new`、`/switch`、`/groupnew` 在「当前会话有 Agent 正在运行」时的行为重新定形：动机、旧行为的完整竞态链路、新实现与验证结果。

---

## 背景：三条指令与运行中 Agent 的旧交互

排查起点是一个问题：「Agent 正在运行时发 `/new`、`/reset`、`/switch` 会怎样？」逐层读码后确认，三条指令都不进 LLM 子阶段（handler 末尾的 `event.should_call_llm(True)` 是阻止默认 LLM 请求的语义，见 `process_stage/stage.py` 的 `not event.call_llm` 判断）、也不抢会话锁（锁只在 agent 子阶段内获取），因此 Agent 再忙它们也能立即执行——但三者对运行中 Agent 的处置各不相同，且都有问题。

### 关键机制（读码结论）

- **事件注册表**（`astrbot/core/utils/active_event_registry.py`）：pipeline 调度器在每个事件进入时 `register`、结束时 `unregister`。`stop_all(umo, exclude)` 对同会话其他活跃事件调 `event.stop_event()`——**只终止事件传播，不会立刻中断生成**。
- **停止信号 watcher**（`astrbot/core/astr_agent_run_util.py` 的 `_watch_agent_stop_signal`）：`run_agent` 每步起一个 0.5 秒轮询的 watcher，发现 `is_stopped()` / `agent_stop_requested` / `agent_force_stop` 才对 runner `request_stop()`。
- **落库目标快照**：`_save_to_history` 写的是 `req.conversation.cid`（请求构建时绑定的对话），不是保存时的「当前对话」；写入内容是 `run_context.messages` 全量，且 `update_conversation` 是整段覆盖。
- **落库门槛**（`internal.py:835`）：`not event.is_stopped() or agent_runner.was_aborted()`——事件被停止但 runner 确实中止了，照样落库。

### 旧 `/reset`：清空被写回复活（实质 bug）

`commands/conversation.py` 的 `reset` 旧实现：`stop_all` → 立即 `update_conversation(umo, cid, [])` 清空 → 清群聊消息历史 → 置清理标记 → 回复「清除聊天历史成功！」。全程不等旧任务收尾（对比：软打断路径和 `/stop` 都有等待或立即停 runner 的设计，reset 没有）。

而旧 Agent 侧：watcher 最多 0.5 秒后发现 `is_stopped()` → `request_stop()` → runner 中止 → 落库门槛通过（`was_aborted()` 为真）→ `_save_to_history` 把「旧历史 + 本轮已发送部分 + 停止标记」全量写回 `req.conversation.cid` 快照——**正是刚被清空的同一个对话**。时序上 watcher 的 0.5 秒延迟远大于 reset 的毫秒级 DB 写，写回几乎必然后到：用户看到「清除成功」，历史却整段复活，还多了一条打断标记。只有在极窄窗口里（LLM 恰好在停止信号生效前后正常完成、`was_aborted()` 为假）才走「不落库」分支，那轮对话凭空消失。

### 旧 `/new`：硬停但旧回复还在发

`stop_all` 后新建对话并切换会话映射。旧 Agent 中止后写回 `req.conversation.cid` 快照 = 旧对话，新对话不被污染（快照机制恰好兜住），但停止信号生效前的约 0.5 秒窗口里旧回复还会继续分段发给用户；旧对话里则留下被截断的内容与打断标记。

### 旧 `/switch`：完全不问运行状态

没有任何停止逻辑，只校验序号后切换 `sel_conv_id` 映射。运行中的 Agent 继续生成、继续推送，完成后照常写回旧对话（快照机制保证不污染新切过去的对话），后续新消息要么排队等会话锁、要么（开了「新消息打断回复」时）先软打断旧任务。用户侧的体感就是「切了对话，旧任务还在后台偷偷跑」。

## 设计决策

用户定形（2026-10-14 讨论）：

1. **`/reset`**：reset 了、上下文清空了，语义上就不再需要当前 Agent 运行、不需要当前上下文——**直接强制停止并清空**。
2. **`/new`、`/switch`**：保留当前上下文，不该静默切换——**运行中拒绝执行**，提示「⚠️ 当前会话有Agent正在运行，请等待结束或发送{第一个唤醒前缀}stop停止后重试」。文案刻意给用户两个选项（等待 / 停止）而不是指挥用户必须停止。无运行任务时正常执行。

## 改动内容

### 1. `/reset` 强制停止 + 写回丢弃（`conversation.py` reset 分支）

替换原 `stop_all` 为 `/stop` 同款强制停止，随后清空逻辑不变：

```python
stopped_count = active_event_registry.request_agent_stop_all(
    umo,
    exclude=message,
    extra_updates={
        "agent_force_stop": True,
        "_discard_history_write": True,
    },
)
# 立即打断活跃 runner，避免仅靠 0.5s 轮询 watcher 才停
active_runner = get_active_runner(umo)
if active_runner is not None:
    active_runner.request_stop()
```

要点：

- **`request_agent_stop_all` 而非 `stop_all`**：软停不终止事件传播，后续收尾（含发送链路清理）正常走，只置 `agent_stop_requested` + 额外标记。`agent_force_stop` 让被停任务按 `/stop` 的「已发送内容截断」语义收尾发送侧（已在发送链路中的内容不拦）。
- **`_discard_history_write` 是新增的事件 extra 标记**：reset 专用的落库丢弃信号，区别于 `/stop` 的「按已发送内容落库」。
- **直接 `runner.request_stop()`**：复用 `/stop` 的立即打断设计，不等 0.5 秒轮询 watcher，把「旧回复继续分段发出」的窗口压到最小。
- 第三方 Agent（dify/coze/dashscope/deerflow）分支保持原 `stop_all` + 删会话 key 不变：那类 runner 不走 internal 落库路径，不存在写回竞态。

### 2. 落库侧丢弃检查（`internal.py` `_save_to_history` 入口）

```python
# /reset 强制停止：上下文已被清空，本轮不再写回，防止覆盖刚清空的历史
if event.get_extra("_discard_history_write"):
    logger.info("任务已被 reset 停止，丢弃本轮历史写回: umo=%s", ...)
    return
```

放在 `if not req or not req.conversation` 检查之后、一切落库分支之前，任何路径（正常完成、中止、LLM 出错兜底落库）都拦得住。

### 3. `/new`、`/switch`、`/groupnew` 运行中拒绝（`conversation.py` 新增 `_reject_if_agent_running`）

```python
def _reject_if_agent_running(self, message, umo=None) -> bool:
    target_umo = umo or message.unified_msg_origin
    running = has_active_runner(target_umo)   # runner 尚未收尾
    if not running:
        running = active_event_registry.has_active(target_umo, exclude=message)
    if running:
        message.set_result(MessageEventResult().message(
            f"⚠️ 当前会话有Agent正在运行，请等待结束或发送{获取第一个唤醒词()}stop停止后重试"
        ))
        return True
    return False
```

要点：

- **双口径判定**：`has_active_runner`（follow_up 的 runner 注册表，覆盖「事件已注销但 runner 还在收尾」的 0.5 秒窗口）+ `has_active`（活跃事件注册表，排除发起指令的事件自身，防抖等待中的事件也不算）。两个都查，单查其一都有缝隙。
- **`/new`**：原 `stop_all` 一并移除——运行中直接拒绝，无需再硬停。
- **`/switch`**：在序号解析之后、取对话列表之前检查，无运行任务时行为与旧版一致。
- **`/groupnew`**：检查**目标群会话**（构造出的 `MessageSession` UMO）而非管理员自己的会话——管理员那边在跑不影响给别的群建新对话（测试钉住此行为）。`umo` 参数即为此设计。
- 唤醒词走 `获取第一个唤醒词()` 实时读取用户配置（与 `/help` 等指令同源），文案中的 `{第一个唤醒前缀}` 随配置变化。

### 与 `/stop` 的语义分工

| 指令 | 停止方式 | 落库策略 |
| --- | --- | --- |
| `/stop` | 软停 + 立即打断 runner | 按已发送内容落库，追加英文停止标记 |
| `/reset` | 同上 | **整轮丢弃**（`_discard_history_write`），随后清空历史 |
| `/new`（运行中） | 不停止 | 拒绝执行，提示等待或 `/stop` |
| `/switch`（运行中） | 不停止 | 拒绝执行，同上 |

## 验证

新增 `tests/test_reset_new_switch_agent_running.py`（11 项，直接运行或 pytest 均可）：

- `test_reset_运行中_强制停止并丢弃写回`：断言 `request_agent_stop_all` 收到 `agent_force_stop` + `_discard_history_write` 双标记、runner 立即 `request_stop`、清空 `update_conversation(umo, cid, [])` 照常执行、回复「清除聊天历史成功」。
- `test_reset_无运行任务_不触发停止`：停止逻辑照走（幂等）但清空不受影响。
- `test_save_to_history_丢弃标记_不写库` / `test_save_to_history_无标记_正常写库`：落库侧两态钉住。
- `test_new_运行中_拒绝执行` / `test_switch_运行中_拒绝执行`：活跃事件口径拒绝，`new_conversation` / `switch_conversation` 未被调用，文案逐字断言。
- `test_new_runner活跃_同样拒绝`：活跃事件已注销但 runner 还没收尾的窗口也拒绝。
- `test_new_无运行_正常创建` / `test_switch_无运行_正常切换`：放行路径回归。
- `test_groupnew_目标会话运行中_拒绝` / `test_groupnew_当前会话运行_目标空闲_放行`：目标会话口径钉住。

测试环境要点（本机坑位）：唤醒词文案断言须钉 `astrbot.core.astrbot_config` 为 `{"wake_prefix": ["/"]}`（`获取第一个唤醒词()` 函数内 `from astrbot.core import astrbot_config`，钉模块属性才有效；本机真实配置首项是「，，」，不钉时 pytest 与直跑结果会随环境漂移——已用 autouse fixture + 直跑包裹两层覆盖）；reset 路径读 `sp.get_async`（alter_cmd 权限配置），须桩成返回 `{}`，否则会初始化真实 SQLite。测试在 Windows 项目 venv 直接跑（`pytest tests/` 与单文件直跑均可）。

## 影响面与兼容性

- **用户可见变化**：Agent 运行中发 `/new`、`/switch`、`/groupnew`（目标群运行中）会收到拒绝提示；`/reset` 会立即停止 Agent 且其本轮不落库（此前历史可能被「复活」）。无运行任务时三条指令行为与旧版完全一致。
- **插件兼容性**：`_discard_history_write` 是事件 extra 上的约定标记，仅框架 internal 落库路径消费；插件自管落库不受影响。`_reject_if_agent_running` 为内置指令私有方法，无插件 API 变化。
- **数据库**：无 schema 变更。
