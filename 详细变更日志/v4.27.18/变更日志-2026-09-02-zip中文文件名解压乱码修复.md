# [2026-09-02] zip 中文文件名解压乱码修复

## 问题现象

更新 ldm（或 CLI 安装插件）后，压缩包里的中文文件名/目录名变成乱码，例如「详细变更日志」解压后变成「Φ»ªτ╗åσÅÿµ¢┤µùÑσ┐ù」。直接用 unzip 或文件管理器查看同一个压缩包，中文显示却完全正常——Windows 上查看某些包也正常。

## 根因

ZIP 格式规范规定：条目未设置 UTF-8 标志位（通用位标志 0x800）时，文件名编码未知，Python `zipfile` 模块此时一律按 cp437（西文 DOS 编码）解码文件名。

- 本项目发版包由 Info-ZIP 3.0 打包，中文条目全部不带 UTF-8 标志位（实测 ldmbot.zip 内 29 个中文条目全中招）；
- Windows 中文环境的压缩工具按本地 GBK 打包的压缩包同样不带该标志；
- Linux 的 unzip、文件管理器不做编码判定、按字节透传（或按 UTF-8 显示），所以「看压缩包正常、Python 解压乱码」。

修复思路：zipfile 按 cp437 强解的文件名可以无损还原出打包时的原始字节（`filename.encode("cp437")`），再按 utf-8 → gbk 顺序重试解码（utf-8 优先：跨平台包的中文名多为 UTF-8 字节；gbk 兜底：Windows 中文环境本地打包）。两者都解不出则保持原样不动，绝不抛异常。

## 修复内容

新增公共工具 `astrbot/core/utils/zip_fix.py`：

- `fix_zip_entry_names(zf)`：就地修补 ZipFile 中无 UTF-8 标志位条目的文件名，须在读取 namelist()/解压之前调用；
- 修补后同步重建 `NameToInfo` 映射——`extract()/extractall()/read()/open()` 都按名查条目，只改 `info.filename` 不同步字典会直接 KeyError（测试环节抓出的真实坑）。

接入的全部解压点（解压前先修补条目名）：

| 文件 | 覆盖场景 |
|------|----------|
| astrbot/core/zip_updator.py / zip_updater.py | 核心更新 unzip_file |
| astrbot/core/updator.py | ldm_AstrBot 更新包应用（apply_update_package）+ unzip_file |
| astrbot/core/star/updator.py / star/updater.py | 插件安装/更新 |
| astrbot/core/dashboard_assets.py | WebUI 包解压（_extract_package） |
| astrbot/core/utils/io.py | WebUI 包解压（extract_dashboard） |
| astrbot/core/utils/update_rollback.py | 回滚恢复解压（该模块禁依赖 astrbot 包，内联同等逻辑 _修复压缩包文件名） |
| astrbot/core/skills/skill_manager.py | 技能包安装 |
| astrbot/cli/utils/plugin.py | CLI 插件安装 |

带 UTF-8 标志的条目、纯 ASCII 条目完全不受影响（修补数为 0，零开销跳过）。

## 新增测试

`tests/test_zip_filename_fix.py`，7 个场景：

1. UTF-8 字节、无标志（本项目发版包形态，手写字节流模拟 Info-ZIP）
2. GBK 字节、无标志（Windows GBK 工具打包形态）
3. 带标志的正常中文条目不受影响
4. 纯 ASCII 条目不受影响
5. GBK 无标志包端到端解压落盘文件名正确
6. 按修补后的名字 read() 可正常读取（NameToInfo 同步验证）
7. 无法解码的字节保持原样、不抛异常

另用真实发版包 ldmbot.zip 做端到端验证：29 个中文条目修补后「详细变更日志/」「从官方迁移教程.txt」等正确落盘。
