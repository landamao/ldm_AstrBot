# [2026-09-14] /compact 参数解析崩溃修复与压缩前提示

> 本文件为独立变更日志，记录 2026-09-14 一次 `/compact` 指令修复：
> 数字参数（如 `/compact 4`）必崩的 TypeError 修复、压缩执行前先发送
> 「正在压缩」提示、`0`/负数轮数归入用法提示。

---

## 问题现象

1. 发送 `/compact 4`（以及任何带数字参数的形式）直接报错， bot 无任何回复，
   后台日志：

   ```
   File "astrbot/builtin_stars/builtin_commands/commands/conversation.py", line 198, in compact
       if parsed is not None and parsed > 0:
   TypeError: '>' not supported between instances of 'tuple' and 'int'
   ```

2. 走 LLM 摘要的压缩耗时较长（需等待压缩模型返回），期间会话里全程无反馈，
   容易以为指令没生效而重复发送。

## 根因

### 问题 1：`转整数或None` 返回值被当标量使用

- `param_utils.py` 里 `转整数或None()` 的返回值是 `(值, 错误提示)` 二元组，
  同文件 `/switch` 的用法 `num, err = 转整数或None(...)` 是正确的；
- 2026-09-13 新增 `/compact` 时写成 `parsed = 转整数或None(token)`，于是
  `parsed` 拿到的是元组（如 `(4, "")`）：
  - `parsed is not None` 恒为 True（元组不是 None）；
  - `parsed > 0` 变成 tuple 和 int 比较 → `TypeError`；
- 因此**任何**非 `yes` 的参数（数字、乱码、空串）都会在解析处崩溃，带数字的
  用法无一幸免。

### 问题 2：压缩执行前无任何提示

- `compact()` 只在全部处理完成后 `set_result()` 一次性回复；
- LLM 摘要路径要等压缩模型返回（可达数十秒），期间用户侧零反馈。

## 修复内容

### 参数解析（`conversation.py`）

- 改为按约定解包：`parsed, err = 转整数或None(token)`；
- `err` 非空（无法解析为数字）→ 回「参数无法识别」用法提示并终止；
- 顺手收紧：`0`/负数轮数（如 `/compact 0`）此前会静默忽略该参数、当作
  不带 N 执行，与帮助文案「保留最近N轮」语义矛盾，现同样归入用法提示；
- `yes/y/是` 分支与「未传参」行为不变。

### 压缩前提示（`conversation.py`）

- LLM 摘要路径在调用压缩模型前，先经 `event.send()` 即时发送：
  `正在压缩上下文（LLM 摘要（保留最近 N 轮）），请稍候…`（N 为实际生效的
  保留轮数，来自显式参数或配置默认；未生效时不带该后缀），
  完成后照旧由 RespondStage 投递「上下文压缩完成」结果消息，两条都有；
- 发送模式沿用 `llm.py` / `alter_cmd.py` 既有的
  `await event.send(MessageChain().message(...))` 写法；`event.send()` 置位的
  `_has_send_oper` 不影响 RespondStage 对 `set_result` 结果的投递；
- 按轮次截断路径（`/compact yes`）是本地操作无耗时，不追加提示。

## 验证

- `tests/test_compact_command.py` 6 例全过：非数字参数回用法提示（修复前此用例
  直接 TypeError）、`0`/`-2` 回用法提示、`yes abc` 混合参数报错、无历史对话提示、
  LLM 摘要先发提示再发结果且 `keep_recent_rounds=4` 正确传入压缩器、未指定 N 时

- 需重启 ldm 生效；修复前线上任何 `/compact <数字>` 均不可用，修复后无需
  处理存量数据（该指令不涉及落库格式变更）。
