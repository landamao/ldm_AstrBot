# [2026-10-14] 启动期不再加载三家 LLM SDK（类型注解改 TYPE_CHECKING）

> 本文件为独立变更日志，记录 `astrbot/core/provider/entities.py` 顶层 SDK 导入改为类型检查期导入的动机、实测数据与兼容性。

---

## 动机

`astrbot/core/provider/entities.py` 在模块顶层导入了三家 LLM SDK 的响应类型：

```python
from anthropic.types import Message as AnthropicMessage
from google.genai.types import GenerateContentResponse
from openai.types.chat.chat_completion import ChatCompletion
```

这三个名字**只出现在类型注解里**（`LLMResponse.raw_completion` 字段与其 `__init__` 形参）。该文件第一行就是 `from __future__ import annotations`，所有注解在运行时都是字符串、不求值；全代码库也不存在任何 `get_type_hints` / `dataclasses.fields` 驱动的注解解析，因此这三行导入在运行期没有任何实际用途。

代价却很大。在「核心已加载」的进程里实测其边际占用：

| SDK | 边际 RSS | 独立导入 RSS |
| --- | --- | --- |
| `openai` | +27.7 MB | 51.9 MB |
| `anthropic` | +19.6 MB | 50.2 MB |
| `google.genai` | +64.9 MB | 111.2 MB |
| **合计** | **+112.2 MB** | 213.3 MB |

也就是说，用户哪怕只用 OpenAI 兼容接口，也要为三家的 SDK 付费。

## 改动内容（astrbot/core/provider/entities.py）

三个导入移入 `if TYPE_CHECKING:` 块，并加注释说明原因（避免后人「顺手」挪回顶层）：

```python
from typing import TYPE_CHECKING, Any

if TYPE_CHECKING:
    from anthropic.types import Message as AnthropicMessage
    from google.genai.types import GenerateContentResponse
    from openai.types.chat.chat_completion import ChatCompletion
```

## 实测效果

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| `import astrbot.dashboard.server` | 250.0 MB | **156.3 MB** |
| 核心 + WebUI + 28 个插件 + provider 实例化 | 356.9 MB | **229.6 MB** |

第二行是按本机真实配置（5 个 `openai_chat_completion` 源 + 1 个 openai embedding + 1 个 openai whisper）测的端到端结果，其中也包含本次同批次的插件侧改动（`pypinyin`、`yt_dlp` 按需化）：`openai` 会在 provider 实例化阶段被动态导入回来，`anthropic` 与 `google.genai` 则彻底不再加载。

## 兼容性

- **纯延迟，无功能变化**：SDK 在首次真正使用对应 provider 时加载——`provider/manager.py` 的 `load_provider()` 本就通过 `dynamic_import_provider()` 按 `type` 动态导入 `sources/*.py`，因此三家 SDK 会在需要时被正确拉起来。
- 启动时若配置了对应 provider，导入发生在 provider 实例化阶段而非核心导入阶段，总内存不变（只是不用的那几家不再付费）。
- 类型检查器（pyright）与 IDE 补全行为不变：`TYPE_CHECKING` 块内的名字对静态分析可见。

## 测试

- 全量 `pytest tests/` 408 项全过。
- 探针验证：改动后 `sys.modules` 中 `openai` / `anthropic` / `google.genai` 均不在启动期加载；`astrbot.dashboard.server` 导入 RSS 从 250.0 MB 降至 156.3 MB。
- 探针验证：模拟 provider 实例化（导入 `openai_source` 与 `openai_embedding_source`）后 `openai` 正常加载，`anthropic` / `google.genai` 仍未加载。

## 回归点

- 该文件（以及任何 `from __future__ import annotations` 的模块）里的 SDK 类型若**只在注解中使用**，一律放 `TYPE_CHECKING`；一旦需要在运行时构造或 `isinstance` 判断，就必须真导入。
- 反例参考：`mcp` 未做此改动——`ToolExecResult = str | mcp.types.CallToolResult` 是运行时求值的类型别名，且 `astr_agent_tool_exec.py` 会真实构造 `mcp.types.CallToolResult(...)` 并对其做 `isinstance`，硬改要动十余个文件且工具一跑仍会加载，收益（14.6 MB）与风险不成比例。
- 新增 provider 适配器时不要在 `entities.py` 或任何核心启动路径上引入新的 SDK 顶层导入。
