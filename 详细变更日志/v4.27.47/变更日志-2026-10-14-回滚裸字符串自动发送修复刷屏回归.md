# [2026-10-14] 回滚「handler 裸字符串自动发送」，修复 v4.27.46 群聊刷屏回归

> 本文件为独立变更日志，记录 v4.27.46 上线后群聊刷屏回归的完整根因链路、回滚决策依据与验证结果。

---

## 事故现象

用户在服务器上更新 v4.27.46 后，群里随便发一条消息（哪怕只发「1」）就疯狂刷屏输出，直到会话被限流才停。日志特征：

- `core.event_bus:99`（**收到新事件**的日志）里反复出现「Hermes 适配器状态: …」「请输入task参数（任务描述）」「请输入 command 参数（指令名）」——这些是机器人自己刚发出的内容，又被当成新消息进入管线；
- `rate_limit_check.stage:109` 连续刷限流丢弃；
- 单机器人群只刷一轮就停；**同一个群有两个机器人实例时互相触发、无限循环**。

## 根因链路（两个独立缺陷叠加成环）

### 缺陷一：装饰器堆叠导致 LLM 工具被同时注册成普通消息事件处理器（上游历史行为）

插件常见的写法是把 `@filter.platform_adapter_type` 叠写在 `@filter.llm_tool` 之下：

```python
@filter.llm_tool("hermes_agent")                                          # 后执行
@filter.platform_adapter_type(filter.PlatformAdapterType.AIOCQHTTP)      # 先执行
async def llm工具_hermes_agent(self, event, task: str = "") -> str: ...
```

装饰器自下而上执行：`platform_adapter_type` 先跑，`get_handler_or_create` 以 `EventType.AdapterMessageEvent`（普通消息事件）类型把该函数注册进 `star_handlers_registry`，事件过滤器只有 `PlatformAdapterTypeFilter`；随后 `llm_tool` 再跑，按 handler 全名查到同一条 metadata 复用，把 handler 塞进 LLM 工具表——**但没有纠正事件类型**，那条「这是普通消息处理器」的注册记录原样保留。

后果：`waking_check` 阶段遍历 `AdapterMessageEvent` 处理器时这些 LLM 工具函数也被遍历到，而 `PlatformAdapterTypeFilter.filter()` 对任何 aiocqhttp 消息无条件放行（与消息内容、是否唤醒无关）。于是**每条群消息都会激活全部 4 个 Hermes LLM 工具函数**（hermes_agent / execute_plugin_command / hermes_status / list_plugin_commands），并置位 `is_wake=True`。误调用时框架只传 `(event)`，工具参数走默认空串，命中提前返回分支：

```python
if not task:
    return "请输入task参数（任务描述）"   # ← 刷屏文案的出处
```

此行为自上游初始提交就存在，**不是 v4.27.46 引入**。

### 缺陷二：v4.27.46 的「裸字符串自动发送」把误激活变成刷屏（本次回归的直接原因）

v4.27.46 在 `call_handler` 的生成器与协程两个分支各加了 `isinstance(ret, str)` 判断：handler 产出裸字符串就 `event.set_result(ret)` 发送。正常 LLM 工具调用走 `astr_agent_tool_exec.call_local_llm_tool` 独立链路（`return str` 进下一次 prompt），不经过 `call_handler`；但消息 handler 链路（`star_request.py`）经过。误激活的 LLM 工具在 `call_handler` 里是协程，`return "请输入task参数…"` 被 `set_result` 发出。

### 成环机制：双机器人互相触发

发出的提示文案本身是一条群消息，成为同群另一个机器人实例的新输入 → 对方也被误激活发出 4 条 → 又回到本机 → 指数放大直到限流。单机器人群没有第二个消费者，故只刷一轮。与 NapCat 自身消息上报无关（用户已验证）。

## 回滚内容

`astrbot/core/pipeline/context_utils.py` 的 `call_handler` 两个分支移除裸字符串识别，恢复 v4.27.45 行为（裸字符串产出静默丢弃）；`tests/test_yield_plain_str.py`（173 行）一并删除。`set_result` 接受 `str` 的能力保留（外部调用方语义未变，只是 `call_handler` 不再自动把产出字符串路由过去）。

## 取舍记录

- 备选方案 B（修缺陷一：`register_llm_tool` 注册时阻止复用消息事件注册）被否：动注册表核心语义，影响所有装饰器组合（`@filter.command` 叠 `llm_tool` 等），需要大范围回归，且「回显成环」的另一半仍需依赖插件写法，收益不匹配风险。
- 误激活本身未根治：LLM 工具仍会在每条消息上空跑一遍（函数体轻、返回值被丢弃），开销可忽略；根治需调整装饰器堆叠的注册语义，留待后续单独评估。
- 该特性回滚后，插件作者写 `return "文本"`（不 yield plain_result）回到静默无效——与 v4.27.45 及之前一致。

## 验证

- `git diff f4b1b12~1 -- astrbot/core/pipeline/context_utils.py` 确认该文件恢复至与 v4.27.45 完全一致。
- 全量测试通过（`pytest tests/`），`ruff check` 无告警。

## 回归点

- 若未来重启「裸字符串自动发送」特性，必须先解决缺陷一（LLM 工具不得被注册为 `AdapterMessageEvent` 处理器），否则本事故必然复现。
- `PlatformAdapterTypeFilter` 对消息无条件放行是设计行为（平台过滤），问题在注册类型而非过滤器本身。

## 修改文件清单

1. `astrbot/core/pipeline/context_utils.py` — `call_handler` 两分支移除裸字符串识别（恢复 v4.27.45 行为）
2. `tests/test_yield_plain_str.py` — 删除（特性配套测试）
