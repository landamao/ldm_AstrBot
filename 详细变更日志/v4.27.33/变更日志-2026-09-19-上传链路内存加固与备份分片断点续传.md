# [2026-09-19] 上传链路内存加固与备份分片断点续传：整读路径清零、分片防损坏与可续传、附件上限补回

> 本文件为独立变更日志，记录 2026-09-19 对照上游 AstrBot PR #10123
> （fix(dashboard): bound upload memory and add resumable chunked uploads，
> 2026-09-18 合并）手动移植的一次上传链路加固：
> 上传请求体不再有整块读进内存的路径、备份分片上传支持断点续传与防损坏、
> WebChat 附件补回缺失的大小上限。按用户决定不移植 WebChat 附件的分片上传部分。

---

## 问题现象

1. 备份整文件直传端点（`/api/v1/backups/upload` 等，前端不使用但一直暴露）
   会把整个请求体一次性读进内存：`_save_upload` 的兜底分支对上传对象执行
   `data = await file.read()`，上传 500MB+ 的备份时内存出现同等量级的尖峰；
   skills 上传的 `_save_upload` 有一份同样的整读分支；
2. 全服没有任何请求体大小限制：`server.py` 里的
   `app.config["MAX_CONTENT_LENGTH"] = 128MB` 是 Flask 时代遗物，
   FastAPI/hypercorn 不会读它，任何端点都可以被灌进任意大的请求体；
3. 备份分片上传（低带宽服务器导入 542MB 备份的真实路径）没有续传：
   前端 1MB×5 并发，任何一个分片请求失败，整个上传作废、从头再来；
   单分片也没有重试；
4. 分片落盘直接以 `"wb"` 打开 `{index}.part` 覆盖写：同索引重传如果中途失败，
   会把已经收好的分片截断损坏；并发重试可能交错写坏分片；
   合并时只检查分片数量，不校验总大小；
5. 上传会话不绑定用户：任何持有登录态的调用方可以传片、合并、取消
   任意会话，还能通过报错差异探测会话是否存在；
6. WebChat 附件上传没有任何大小上限——上游旧版本还有「落盘后超限删除」的
   后置检查，魔改版里连这个检查都不存在。

## 根因

- 魔改版的分叉点早于上游这轮上传加固：整读兜底分支、无限制的请求体、
  「数量对就合并」的朴素分片逻辑都是分叉时的上游原样；
- `MAX_CONTENT_LENGTH` 生效是 Flask 的行为，从 Flask 迁移到 FastAPI 后
  这行配置变成了无人读取的死配置，制造了「有 128MB 上限」的假象；
- Starlette 的表单解析会把大 body 暂存到磁盘（SpooledTemporaryFile），
  所以解析阶段不吃内存；真正的内存尖峰来自解析之后的 `file.read()` 整读；
- 附件上限缺失是魔改早期改动中丢失的（上游 pre-PR 版本尚有后置检查）。

## 修复内容

### 共享流式落盘工具（`astrbot/core/utils/upload.py`，新增）

- `save_upload_stream`：1 MiB 块循环写入；`max_bytes` 在写入中途强制校验，
  超限删临时文件抛 `UploadTooLargeError`；先写唯一命名的兄弟临时文件，
  全部成功后 `os.replace` 原子改名，失败只清理自己的临时文件，
  绝不破坏已有目标文件（如覆盖上传同名附件的场景）。

### 三个上传适配器统一接契约

- `api/multipart.py`（UploadFileAdapter）、`asgi_runtime.py`（RequestUploadFile）、
  `api/web.py`（PluginUploadFile，插件 Web API 面向插件暴露的同一套适配器）
  的 `save()` 统一改为 `save(destination, *, max_bytes=None) -> int`，
  委托 `save_upload_stream`，返回写入字节数。

### 请求体预检中间件（`server.py`）

- `_check_body_limit` 纯函数 + `dashboard_body_limit_middleware`：
  默认上限取 `MAX_CONTENT_LENGTH`（128 MiB，这回真的生效了），
  按路由前缀覆盖表更具体的前缀在前；
- multipart 请求无 Content-Length 直接 411：表单解析会先把大 body 暂存磁盘，
  必须在解析前拿到长度才能提前拦截；仅对 POST/PUT/PATCH 生效，
  GET（日志 SSE 客户端会带垃圾 multipart Content-Type）不受影响；
- 媒体类型用 `python_multipart.parse_options_header` 判定，
  与表单解析器同一套规则，前导空格的 ` multipart/form-data` 无法绕过；
- 覆盖表：备份分片 2 MiB、`/api/v1/files` 与 `/api/chat/post_file` 与
  知识库上传 512 MiB+1 MiB multipart 框架余量、插件配置文件 500 MiB+余量
  （余量保证恰好压线的文件不会被 413 误杀）。

### 通用分片上传会话管理（`chunked_upload_service.py`，新增）

- 会话绑定 `owner`（登录用户名）与 `purpose`（业务标识）；
  不存在/已过期/他人会话统一报同一错误，无法探测；
- 分片保存：唯一临时名 → `save(max_bytes=chunk_size)` → 字节数复核
  （短写拒绝）→ `os.replace` 原子发布 → 登记已收；同索引重传失败
  不影响已收分片，乱序到达幂等；
- `session_status`：只读返回已收分片、总数、分片大小与剩余有效期；
  有意不刷新 `last_activity`，轮询续传状态不会给会话续命；
- `assemble`：合并后复核总大小与声明一致，失败删产物；
- 过期：滑动 1 小时空闲窗口 + 5 分钟一轮的看门狗；目录删除失败时
  会话保持登记让看门狗重试，成功后摘除；`abort` 对过期会话仍然有效
  （清理本来就是目的），对他人会话无效。

### 备份上传（`backup_service.py` / `api/backups.py`）

- 直传端点改走 adapter + `max_bytes=128 MiB`，超限提示走分片上传；
  分片初始化拒绝超过 8 GiB 的声明总量（提示 FTP/SFTP 复制到 backups 目录）；
- `upload_init/chunk/complete/abort` 全部委托分片服务并透传 `owner`，
  新增 `upload_status`；`/api/v1/backups/upload/status` 与
  `/api/backup/upload/status` 两条路由同步新增；
- 删除本地旧的 `upload_sessions` 字典、过期清理协程与 `_save_upload` 整读分支；
  导出防覆盖（`resolve_export_zip_path`）、并发导出拒绝、下载票据等
  既有魔改全部保留。

### 顺手小改

- `skills_service`：删除 `_save_upload` 整读兜底，直接 `await file.save(...)`
  （调用方传入的已是流式 adapter）；
- `config_service`：插件配置文件上传从「落盘后超限再删」改为写入中拦截；
- `chat_service`：补回 `MAX_UPLOAD_FILE_SIZE_MB = 512`，附件保存前按
  Content-Length 快速拒绝 + 写入中强制上限；
- `stores/common.js`：SSE GET 请求头里无意义的 multipart Content-Type 移除。

### 前端断点续传（`useChunkedUpload.ts` 新增 / `BackupDialog.vue`）

- 调度器持有会话状态：并发 5、每片静默重试 3 次；run-generation 防护
  保证旧运行的迟到完成不计入新运行的进度；取消时排空在途请求再退出；
- 失败不再自动 abort 会话：导入页出现「继续上传」按钮，
  先查 `status` 拿已收分片，只补传缺失分片；会话已过期则自动重新初始化；
  complete 阶段失败视为会话不可信，续传时自动换新会话；
- `resetImport` 通过 `uploader.cancel()` 统一清理（包括失败后可续传的会话）；
- 进度条与阶段文案由调度器统一供数，预检查阶段覆盖显示。

### 设计取舍（按用户决定）

- **不移植 WebChat 附件的分片上传**（chat_service 分片全家 +
  ChatInput.vue + useMediaHandling.ts）：魔改版 WebChat 重度分叉冲突大，
  附件通常不大、现有流式直传 + 512MB 上限足够，后续真有需求再补；
- 分片服务的用户可见报错与日志按魔改版惯例使用中文。

## 部署/测试注意

- 后端改动需重启服务生效；前端已构建进 dist，页面强刷一次；
- 部署后 `data/backups/.chunks` 下旧版残留的分片目录会在一小时过期窗口后
  被看门狗自动回收，无需手动清理；
- 低带宽服务器实测建议：上传 500MB 级备份中途断网 → 恢复后在导入失败页
  点「继续上传」，确认从缺失分片继续、总耗时不再从头计时；
- 上传会话有效期 1 小时空闲窗口：中断后超过 1 小时再点「继续上传」
  会自动开新会话从头传，属预期行为。
