# 变更日志 — 2026-11-12 — 恢复结果可判定、错误全量堆栈、目录被占用时说人话

## 背景

备份恢复失败时的可观测性存在四处缺口，用户无法判断到底恢复到哪一步：

- **失败被当成成功**：目录、配置文件、知识库的异常一律 `result.add_warning(...)`，而 `success` 只在 `add_error` 时置 False。插件目录一个都没恢复，任务状态照样 `completed`，WebUI 显示绿色对勾「导入完成」。
- **错误没有堆栈**：`ImportResult.add_error()` 只做 `logger.error(msg)`，异常被 `str(e)` 压平成一行字符串，日志里没有任何 Traceback；权限、编码、文件损坏类问题事后无法定位。
- **内部实现细节糊到界面上**：目录替换失败时 `OSError` 的原文会把中转路径一起带出来，例如
  `[WinError 5] 拒绝访问。: '...\data\plugin_data' -> '...\data\.plugin_data.old-20261112_034619'`，
  用户第一反应是「这个 `.old` 是什么？是不是多出来一个目录？」
- **提示不可执行**：只说「停掉服务用终端恢复」，命令却写死成 `python main.py --restore-backup`。项目用的是 venv 里的解释器，照抄会跑到另一份 Python 上。

## 改动

### 1. 结果可判定（`astrbot/core/backup/importer.py`）

- `ImportResult` 新增 `directory_results: dict[str, dict]`（`status: ok|failed|skipped`、`files`、`error`）与 `set_directory_result()`，`to_dict()` 一并透出。恢复结束后能逐目录看到「恢复了多少文件 / 哪个失败 / 为什么」。
- **失败等级纠正**：目录替换失败、解压失败、配置文件导入失败、知识库导入失败全部从 `add_warning` 改为 `add_error`（`success=False`）。知识库尤其必须显式 —— 它在导入前已被 `_clear_kb_data()` 清空，失败就意味着数据缺失。
- 单个附件、单个文档块、KB 媒体文件失败仍只记 warning（不阻断整体恢复），但改为走 `result.add_warning`，**不再是只写日志、界面上完全看不见**。
- 替换成功后会校验目标目录确实存在，避免「rename 声称成功、目标却不存在」被吞掉。

### 2. 错误全量堆栈（`importer.py` / `backup_service.py` / `main.py`）

- `add_error()` / `add_warning()` 新增 `exc_info` 参数（`BaseException | bool`），所有 catch 到异常的分支统一传 `exc_info=e`：主库导入及回滚失败、知识库清空/导入、配置文件、manifest 解析、ZIP 损坏、目录解压/替换、附件、文档块、KB 媒体与 FAISS 索引。
- `pre_check()` 的 `BadZipFile` / `JSONDecodeError` / 其它异常补 `logger.error(..., exc_info=e)`（此前只把字符串塞进 `result.error`）。
- 服务层「恢复前备份失败」补 `exc_info`；终端 `--backup` 与前置备份失败额外 `traceback.print_exc()`。
- 原则：**日志要全，界面要短**。堆栈只进 `data/logs/ldmbot.log`，用户可见文本保持一句话 + 处置办法。

### 3. 占用识别与提示（`importer.py`）

- `_is_directory_lock_error()`：识别 Windows `winerror in (5, 32)`（拒绝访问 / 共享冲突）与 POSIX `EBUSY`；普通 `EACCES`（真的权限不足）不误判。
- `_detect_directory_holders()`：用 `psutil.Process().open_files()` 反查目标目录下被本进程打开的文件，取首层目录名作为「哪个插件占着」的线索（best-effort，取不到返回空）。
- `_locked_directory_hint()`：按目录给不同建议，且**不再暴露 `.old-*` 中转路径**：
  - `plugin_data` / `plugins` → 「通常是有插件正在运行并占着自己的数据目录（sqlite、日志、缓存等）。[检测到这些插件正在使用该目录：xxx。]请到「插件管理」里禁用相关插件后重试，或者停掉服务后执行 <命令> 恢复。」
  - `knowledge_base` → 「通常是知识库数据库仍被进程持有。请先停止服务，然后在终端执行 <命令> 恢复。」
- `AstrBotImporter` 新增 `suggest_terminal_restore` 构造参数：只有**在服务进程内恢复**（WebUI，`BackupService` 传 True）才提示「停掉服务去终端恢复」；终端恢复本身就在终端里，改为提示「可能还有另一个 ldm 进程或别的程序占用该目录」。
- 目录级失败文案由「现有数据未改动」改为「**该目录保持原样（未替换）**」—— 前者会让用户以为整个恢复没有任何效果，实际前面的主库、配置、其它目录可能已经替换完成。

### 4. 真实恢复命令（`astrbot/core/utils/about_info.py`）

新增 `build_restore_command()`，复用该文件既有的 `sys.executable + sys.argv` 取参方式：

- 解释器用**当前进程真实的** `sys.executable`（venv 路径），不是裸 `python`；
- 脚本用 `get_astrbot_root()/main.py` 绝对路径，不依赖 cwd；打包运行时回退 `sys.argv[0]`；
- 只透传会影响数据位置的 `--data-dir` / `--webui-dir`（含 `--flag=value`），丢弃 `--rollback` 等模式参数，末尾追加 `--restore-backup`；
- 含空格的路径自动加双引号。

产出示例：`D:\...\.venv\Scripts\python.exe D:\...\main.py --data-dir "D:/my data/dir" --restore-backup`

### 5. 失败也回传明细（`backup_service.py` / `main.py`）

- 导入失败时 `_set_task_result(..., result=payload, error=...)` 一并回传，`get_progress()` 在 `failed` 下也返回 `result`（此前只有 `completed` 带）。
- 终端恢复逐目录打印 `已恢复 N 个文件 / 备份中没有该目录，已跳过 / 失败（原因见下方）`；失败汇总改为「恢复未完全成功：以下项目失败。失败的目录保持原样；已恢复成功的部分不会自动回滚。」

## 验证

- `tests/test_backup_roundtrip.py::test_directory_import_failure_keeps_existing_data` 扩展断言：
  - 用户可见文本必须出现「目录正被其他程序占用」与「插件管理」；
  - 必须包含 `sys.executable`（证明命令不是硬编码的 `python main.py`）；
  - `errors` 与 `directory_results[].error` 中不得出现 `.old-`。
- `pytest -k "backup or import_backup"` → **32 passed**。
- 实测占用场景终端输出：结果区 `plugin_data: 失败（原因见下方）`；错误区为友好说明 + 真实恢复命令；全流程输出不再出现 `.old-<时间戳>`，`Traceback` 正常打印。
- 单独验证 `build_restore_command()`：带空格路径自动加引号、`--webui-dir=...` 形式可透传、`--rollback` 被丢弃。

## 说明

- 占用检测是**尽力而为**：`psutil` 只覆盖本进程持有的句柄，锁在其它进程（如插件拉起的子进程）时只能给通用建议。它只用于提示，内部异常全部吞掉，不影响恢复流程。
- `add_error` / `add_warning` 的 `exc_info` 默认 False，未传的老调用点行为不变。
- 界面文案改动属于后端字符串，需重启服务生效；测试断言与日志格式不受影响。
