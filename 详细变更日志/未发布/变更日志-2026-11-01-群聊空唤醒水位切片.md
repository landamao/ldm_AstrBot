# 变更日志 — 2026-11-01 — 群聊空唤醒水位切片

## 背景

只发一个 @（或只发唤醒前缀）的**空唤醒**消息，只有 `At` 组件、没有 `Plain`/`Image`/`Json`，`Main.on_message` 里 `has_context_content` 为假，**不会进群聊缓冲**，因此也没有 `_group_context_record_id` 落位 extra。

v4.27.43 为这种情况加了兜底：`on_req_llm` 里直接 `prompt_idx = len(raw_list)`，把「请求那一刻缓冲里的全部记录」当成历史注入，然后把缓冲 `clear()` 掉。

问题在于 `on_req_llm` 走的是 **LLM 请求时刻**，而不是唤醒时刻。任何在 `on_llm_request` / `on_waiting_llm_request` 里等待的插件都会把这个窗口撑开——本机「消息补获」插件的等待收集新消息默认就要等 6 秒。于是**唤醒之后新到的消息**被当成「唤醒之前的历史」注入，同一批内容又被插件按「本轮新消息」注入一次。

实测现象（群聊只 @ 一下，随后未艾特发一张图）：

- 群聊上下文块里出现 VLM 转述 `[Image: 这张图是…]`，消息补获块里出现 `[图片或表情: D:\...\temp\media_image_xxx.jpg]`，同一张图一轮出现两次；
- 转述在主请求路径上同步阻塞 3.7 秒（`17:53:53.988` 图片入缓冲，`17:53:58.595` 才延迟转述，正好卡在插件 6 秒等待结束、LLM 请求前）；
- 整轮 2982 tokens，其中大半是重复内容。

## 改动

### 1. 缓冲新增平行单调序号（`astrbot/builtin_stars/astrbot/group_chat_context.py`）

`GroupChatContext` 新增：

- `self._record_seq: dict[str, deque[int]]`：与 `raw_records`、`_record_ids` 平行，每条记录一个全局单调序号；
- `self._seq`：进程内自增计数器，`handle_message` 每次 append 前 `+= 1` 并同步 append 到 `_record_seq`；
- 超出 `group_message_max_cnt` 出队裁剪时，三个 deque 一起 `popleft()`；`reset`/清理路径一并 `pop` 掉 `_record_seq`。

用序号而不是下标，是因为裁剪会让下标整体前移：唤醒时记下的「第 3 条」在裁剪两条后已经变成第 1 条，按下标切必然错位。序号只增不减，裁剪也不影响比较。

### 2. 唤醒时刻打水位（`mark_wake_watermark`）

```python
def mark_wake_watermark(self, event: AstrMessageEvent) -> None:
    event.set_extra(_WAKE_SEQ_EXTRA, self._seq)
```

`_WAKE_SEQ_EXTRA = "_group_context_wake_seq"`。语义是「唤醒发生这一瞬间，已分配到第几条记录」，之后新到的记录序号一定大于它。

### 3. 消息阶段打点（`astrbot/builtin_stars/astrbot/main.py`）

`Main.on_message` 在 `has_context_content` 判定之后、群聊上下文注入之前，对所有**群消息**调用 `mark_wake_watermark(event)`。

必须放在消息阶段：`on_llm_request` 可能被插件拖上数秒，那时缓冲里已经混进了本轮的新消息，再打点就失去意义。水位的值不受后续消息影响（`test_mark_wake_watermark_uses_current_seq` 断言）。

### 4. 切点逻辑重排（`on_req_llm`）

原来只有「有落位记录 / 空唤醒兜底全量」两条路，现在按优先级四条：

```text
1. 落位 record_id 在缓冲里     → inject_end = id_list.index(record_id)，消费它本身（keep_from = inject_end + 1）
2. 空唤醒且带水位              → inject_end = bisect_right(seq_list, wake_seq)，不消费（keep_from = inject_end）
3. 空唤醒但无水位（异常路径）  → inject_end = len(raw_list)，维持旧的全量注入语义
4. 有 prompt_idx 但记录已被裁掉 → inject_end = prompt_idx，旧兜底
```

- 第 1 条优先于水位：只发唤醒前缀的空唤醒**会**进缓冲（有 `Plain`），既带 `record_id` 又带水位，必须按记录切，否则会把触发消息自己也当历史（`test_bare_wake_with_record_uses_record_index` 专门构造了「水位落在自己身上」的场景）。
- 第 2 条用 `bisect_right`：`seq_list` 单调递增，直接二分找第一个大于水位的下标，等价于「水位之内有几条」。
- **水位之后的记录不再 `clear()`**，而是原样留在缓冲（`remaining` / `remaining_ids` / `remaining_seqs` 同步回写），下一轮再作为历史出现。空唤醒分支从「注入全部并清空」变成「注入水位之前的、留下之后的」。

## 取舍与已知影响

- 等待窗口内**别人**发的消息，本轮不再注入。若「消息补获」是 scope=本人，这部分内容本轮模型确实看不到；它们会留在缓冲，下一轮作为历史出现，不丢。
- 消息补获侧的图片仍是本地临时路径文本（`[图片或表情: D:\...\xxx.jpg]`），模型看不见图。这属于插件侧问题（应走 `req.image_urls`），本次不动。
- 水位是**每事件一个** extra，不做全局状态，并发多群各自独立；事件被合并/停止时水位随事件走，不需要额外清理。
