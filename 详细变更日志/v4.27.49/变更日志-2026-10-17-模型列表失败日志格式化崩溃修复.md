# [2026-10-17] 修复模型列表获取失败时的日志格式化崩溃

> 本文件为独立变更日志，记录三处 provider 源 `get_models` 异常分支的 logging 占位符错误及其掩盖效应的修复。

---

## 动机

WebUI「获取模型列表」失败时，用户看到的报错是 `not all arguments converted during string formatting`（或日志里出现 `--- Logging error ---`），而不是真实的网络错误（连接拒绝、401、超时等）。

根因与业务逻辑无关：`astrbot/__init__.py` 导出的 `logger` 是标准库 `logging.getLogger("astrbot")`，占位符语法是 `%s`；而 openai/anthropic/gemini 三个 provider 源的 `get_models()` 异常分支误用了 loguru 风格的 `{}` 占位符并附带了位置参数。标准库 logging 内部执行 `msg % args` 时，格式串里没有任何 `%` 转换符，三个参数全部「未被转换」，于是 logging 自身先抛 `TypeError: not all arguments converted during string formatting`。这个二次错误把真正的原始异常顶掉：

- 用户侧（经 `config_service._model_list_error` 透传到前端）：看到的是 `Exception` 的 str 即二次错误文案，完全丢失原因；
- 日志侧：logging 的 `handleError` 打印格式化失败堆栈，原始异常只藏在 `Arguments:` 尾巴里。

`openai_image_generation_source.py` 的同款分支用的是正确的 `%s` 写法——同一批代码里风格不一致，佐证这是笔误而非设计。

## 改动内容（3 个文件）

三处均为「`{}` 占位符 → `%s` 占位符」的单行修正，参数本身不动：

1. `astrbot/core/provider/sources/openai_source.py` `get_models()` 异常分支。
2. `astrbot/core/provider/sources/anthropic_source.py` 同上。
3. `astrbot/core/provider/sources/gemini_source.py` 同上（该处传的是 `e.message`）。

## 验证

- 项目 venv 下直接复现：`{}` 写法触发 `--- Logging error ---` + `TypeError`，与用户所见一致；`%s` 写法输出单行日志，携带提供商 ID、api_base 与原始错误。
- 全库 `grep` 扫描 `logger.*("…{}"` + 位置参数模式，确认无同类残留。
- 修复后人工触发获取模型列表失败（断网/错 key），日志与前端均显示真实原因。

## 兼容性

纯日志分支修正，无接口、无配置、无行为变化。
