# [2026-10-17] 非 ASCII（中文）API Key 透传支持

> 本文件为独立变更日志，记录中文 API Key 在 HTTP 头编码层崩溃的根因、bytes 透传方案及各 SDK 的接入点选择。

---

## 动机

有用户在网关类服务上使用了含中文的自定义密钥，配置保存一切正常（前端无校验、后端无校验、JSON 落库无损），但发起请求时崩溃：

```
UnicodeEncodeError: 'ascii' codec can't encode characters in position 7-10:
ordinal not in range(128)
```

报错隐晦且发生在请求构造期。逐层排查确认卡点在最底层：httpx 的 `_normalize_header_value` 对 str 值强制 `.encode("ascii")`，任何非 ASCII 字符（包括中文密钥、全角字符）都会在此炸掉。openai / anthropic 两个 SDK 内部同样走 httpx，中文 key 从 `api_key` 参数一路变成 `Authorization` / `X-Api-Key` str 头后在这层统一崩溃。aiohttp 则原生支持 UTF-8 头（其序列化器对非控制字符直接 UTF-8 编码），不涉及。

此前用户只能把中文密钥翻译成 ASCII 才能用，无任何绕过手段。

## 方案选型

三个候选：前端/后端校验拒绝非 ASCII key（把问题挡在门外，用户诉求直接落空）；latin-1 透传（把 UTF-8 字节伪装成 latin-1 字符串，httpx 能过但语义脏，且 openai SDK 会在 `api_key` 上再包一层 str 破坏透传）；**UTF-8 bytes 直传**——httpx 头值本就接受 bytes 并原样上线，实测三栈（openai SDK、anthropic SDK、genai SDK）均支持在 headers dict 里放 bytes 且按原字节上线，本地 HTTP 服务器实证服务端可按 UTF-8 还原原文。

定案 bytes 透传：ASCII 密钥原样返回、行为不变；非 ASCII 密钥编码为 bytes 进头。

## 改动内容

### 公共层（1 个文件）

`astrbot/core/provider/provider.py` `AbstractProvider` 新增 `get_wire_key()`：入参为 str 且全 ASCII 时原样返回，否则返回 UTF-8 编码 bytes。挂在 `AbstractProvider` 而非 `Provider`，使 TTS/STT/Embedding/Rerank 各族子类均可复用。

### 四个直接接入的源

1. **`openai_source.py`**（连带 9 个继承子类：openrouter/groq/zhipu/xai/aihubmix/longcat/ssycloud/responses 等）：
   - `__init__`：非 ASCII 时向 SDK 传 `default_headers={"Authorization": b"Bearer " + key}`。openai SDK 的头合并顺序为 `{**auth_headers, **default_headers}`，`default_headers` 后写覆盖，SDK 不再输出 str 版中文头。`api_key` 参数维持原值（SDK 校验要求凭据存在）。
   - `set_key()`：改写 `client._custom_headers`（property 每次重算，直接 mutate `default_headers` 返回值无效）；ASCII 时恢复 SDK 默认认证路径。
2. **`anthropic_source.py`**：
   - `__init__` 与 `set_key()`：非 ASCII 时 `api_key=None` + `default_headers={"X-Api-Key": bytes}`。两个坑：`api_key` 置空串 `""` 时 SDK 的 `_api_key_auth` 仍输出 `{"X-Api-Key": ""}`，与 bytes 头按不同 dict 键并存，线上会发出两个 X-Api-Key 头且 SDK 校验通过后行为不可预期，必须置 `None`；校验 `_validate_headers` 用 dict 大小写敏感的 `.get("X-Api-Key")` 查找，键必须大写 `X-Api-Key`（小写键会被误判为「未设置凭据」抛 TypeError）。
3. **`gemini_source.py`** / **`gemini_tts_source.py`**：genai SDK 在客户端初始化时把 `api_key` 写入 `http_options.headers["x-goog-api-key"]`（str），用户传入的 `http_options.headers` 经 `patch_http_options` 以「后写覆盖」合并。因此非 ASCII 时传 `{"x-goog-api-key": bytes}` 即可整体覆盖，SDK 内部不再触碰该键。`set_key()` 内部走 `_init_client()`，自动重跑同一逻辑。

### 次要源未接入的说明

fishaudio/minimax/nvidia/bailian 等直接手拼 `{"Authorization": f"Bearer {key}"}` 的源（aiohttp 或 httpx 明文 str）未在本版逐一接入：`get_wire_key()` 已就位，接入是每个源两行的机械改动，留待这些通道出现实际诉求时随用随接。embedding/rerank/小众 TTS 使用中文网关密钥的场景概率远低于主聊天通道。

## 验证

- 本地 HTTP 服务器端到端：openai / anthropic / gemini / openai_image_generation 四源，中文 key 初始化 → 切 ASCII → 切回中文，服务端收到的头全部还原为中文原文；set_key 双向切换无残留。
- 新增 `tests/test_non_ascii_api_key.py` 5 项回归（四源上线断言 + get_wire_key 纯函数断言）。
- 全量测试 419 项全过（4.27.48 为 414，+5 为本次新增）。
- `ruff check` 改动文件全过。

## 兼容性

- ASCII 密钥路径一行未动：openai/anthropic/gemini 的初始化参数与此前完全一致。
- bytes 头是 HTTP 线上字节的直接表达，与「服务端按 UTF-8 解码」配合工作；对端若按 latin-1 解码则看到乱码——这是 RFC 9110 obs-text 的固有歧义，主流网关（Nginx/Caddy 等）按字节透传不感知。
- 仅影响非 ASCII 密钥：此前这类配置是「必炸」，不存在兼容旧行为的包袱。
