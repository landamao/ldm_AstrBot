# 新增：插件报错不中断事件配置（plugin_error_continue）

- 日期：2026-09-06

## 背景

插件处理函数（指令/事件监听 handler）抛异常时，事件管线会直接终止整个事件：

- 同一事件后续还未执行的插件 handler 全部跳过（多插件同时监听同一事件时，一个插件坏掉连带其他插件失效）；
- 调度器见到 `is_stopped()` 后，结果装饰、发送等后续 stage 全部中断。

对挂了多个事件监听插件的部署，单个插件 bug 会放大成「整条链路失效」。

## 根因链

`astrbot/core/pipeline/process_stage/method/star_request.py` 的 `except Exception` 分支在记录日志、触发 `OnPluginErrorEvent` 钩子、（唤醒消息时）回复错误文案后，**无条件**调用 `event.stop_event()`：

1. `star_request.py` 循环顶部 `if event.is_stopped(): break` → 后续 activated_handlers 跳过；
2. `pipeline/scheduler.py` `_process_stages` 每层检查 `event.is_stopped()` → 后续 stage 跳过；
3. `process_stage/stage.py` 后续 LLM 调用同样被拦。

其他调用插件代码的路径本就有保护、报错只记日志不中断，不受影响：

- `pipeline/context_utils.py` `call_event_hook`（BaseException 只记日志）；
- `pipeline/result_decorate/stage.py` 的 `OnDecoratingResultEvent` 钩子循环；
- `pipeline/waking_check/stage.py` 的 filter 循环。

因此唯一需要改动的中断点就是 `star_request.py`。

## 改动

### 1. 配置项（`astrbot/core/config/default.py`）

- `DEFAULT_CONFIG` 顶层新增 `"plugin_error_continue": False`（默认关闭，保持现有行为）；
- `CONFIG_METADATA_3` 的 `plugin_group`（WebUI「配置文件 → 插件配置」分区）新增开关：

  - 描述：插件报错不中断事件
  - hint：开启后，插件处理函数报错时仅记录日志，继续执行后续插件和事件流程；关闭时报错即终止该事件。

### 2. 前端 i18n 条目（`dashboard/src/i18n/locales/zh-CN/features/config-metadata.json`）

后端 `config_service.py` 返回 metadata 前会经 `ConfigMetadataI18n.convert_to_i18n_keys` 把 description/hint 替换成 `plugin_group.plugin.plugin_error_continue.description` 这类 i18n key，翻译表在前端语言文件里。若缺条目，前端 `translateIfKey` 对 `plugin_group.*` 缺失翻译返回空串，标签回落到原始键名——WebUI 里就会显示一串英文 `plugin_error_continue`。故须在 `plugin_group.plugin` 下补 `plugin_error_continue` 的 description/hint 中文条目，并重新构建 dashboard。

### 3. 行为（`star_request.py`）

`except` 分支按配置二选一：

```python
# 运行时读取，WebUI 修改后无需重启即生效。
# 继续模式下不发错误文案也不终止：文案一旦发出会置位 _has_send_oper，
# ProcessStage 会认为本事件已有回复而跳过 LLM 请求。
if self.ctx.astrbot_config.get("plugin_error_continue", False):
    continue

if not event.is_stopped() and event.is_at_or_wake_command:
    ret = f":(\n\n在调用插件 {md.name} 的处理函数 {handler.handler_name} 时出现异常：{e}"
    event.set_result(MessageEventResult().message(ret))
    yield
    event.clear_result()

event.stop_event()
```

- **继续模式（开启）**：只记日志 + 触发 `OnPluginErrorEvent` 钩子，然后 `continue` 到下一个 handler——不发错误文案、不终止事件。事件结果保持为空、`_has_send_oper` 未置位，后续插件照常执行，唤醒消息的 LLM 请求也照常进行（报错插件如同不存在）；
- **默认（关闭）**：维持原有行为——唤醒消息回复错误文案并终止事件。

第一版实现保留了错误文案、仅去掉 `stop_event`，实测发现事件虽不终止但 LLM 不再请求：错误文案经 respond stage 发送时 `astr_message_event.send()` 置位 `_has_send_oper`（`astr_message_event.py:293/487`），`process_stage/stage.py:57` 以 `not event._has_send_oper` 为 LLM 兜底请求的前提，于是把「发文案」也收进默认分支，继续模式下不发文案。这也与 hint「仅记录日志」的既有文案一致，前端无需重新构建。

- 在 process 时动态读取 `ctx.astrbot_config`（AstrBotConfig 是 dict 子类，WebUI 保存即原地生效），不学其他 stage 在 initialize 时快照标量值。

### 兼容性

- 已有部署的 `data/config/astrbot_config.json` 无需手动迁移：`AstrBotConfig.check_config_integrity` 启动时自动补默认值 False（与「改 schema 默认值不同步存量配置」的插件坑不同，主配置有自动补键机制）；
- WebUI 需要前端参与：metadata 文案经 i18n key 下发，语言文件须补条目并重新构建 dashboard（见改动 2）；构建会清空 dist，构建后须写回 `dist/version` 与 `dist/assets/version` 两处版本文件；
- 后端改动（metadata + 行为）需重启进程生效；前端更新后浏览器 Ctrl+F5 强刷。

## 验证

新增 `tests/test_plugin_error_continue.py`，三个用例全部通过：

1. **默认关闭**：报错后 `stop_event` 被调用、后续 handler 不执行、唤醒消息仍回复含插件名与异常信息的错误文案；
2. **开启**：报错不中断、后续 handler 继续执行、事件未终止；不发错误文案、事件结果保持为空（`_has_send_oper` 未置位，LLM 兜底请求前提成立）；
3. **非唤醒消息 + 开启**：不发错误文案、后续 handler 继续执行。

i18n 对照：用 `ConfigMetadataI18n.convert_to_i18n_keys` 实跑确认后端生成的 key（`plugin_group.plugin.plugin_error_continue.description/hint`）与前端语言文件 JSON 路径完全一致；`pnpm build` 重新构建通过，产物中 grep 到新条目，`dist/version` 与 `dist/assets/version` 已写回 v4.27.23（与当前代码版本一致，发版时随版本号一起更新）。

注意事项：`method/star_request` 与 `process_stage/stage.py` 互相引用，**测试不能直接 import**，须先 `ensure_builtin_stages_registered()`（与应用真实启动入口一致），否则触发循环导入。
