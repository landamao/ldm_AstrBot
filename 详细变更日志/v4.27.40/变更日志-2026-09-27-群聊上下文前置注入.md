# [2026-09-27] 群聊上下文前置注入：历史块挪到用户消息之前，修时间倒挂

> 本文件为独立变更日志，记录群聊上下文增强（群聊历史记录注入 LLM 请求）的注入位置重构。方案于 2026-09-26 讨论定案，2026-09-27 实施。

---

## 问题现象

开启群聊上下文增强后，注入给模型的群聊记录是 `raw_list[:prompt_idx]`——**全部发生在当前触发消息之前**，但拼装时被追加在用户消息之后（`assemble_context` 写死顺序：prompt → extra parts → 图片/音频），时间序倒挂：

- 模型顺着读会把群聊消息理解成「用户提问**之后**群里才说的话」，与事实相反，可能答错对象、答错时序；
- 群聊块最多 300 条（`group_message_max_cnt`），垫在用户消息身后，把用户消息和它自己的图片/音频隔开，图片归属容易串；
- 原 header「Belows are group chat context after your last reply」一直在做文案对冲，实测仍出现理解出错和「经常看不见历史」。

## 方案取舍

| 候选 | 结论 | 原因 |
| --- | --- | --- |
| 拆成两条 user 消息（上下文一段、用户消息一段） | 否决 | 各家 API 行为不可控：Anthropic 自动合并连续同角色消息（等于白拆）；严格交替的网关/模型直接报错；第一条纯上下文 user 消息还可能被模型当成独立提问。多提供商框架赌不起 |
| 直接把群聊块拼进 `req.prompt` 头部 | 否决 | `req.prompt` 被到处当「用户原始输入」引用：知识库检索 query（astr_main_agent.py:302）、prompt_prefix 拼接（:382）、dify/coze/dashscope/deerflow 等第三方 runner 的对外查询，会连环误伤 |
| 只改提示词（保持现有顺序） | 不足 | 原 header 本身就是在对冲，实测上限有限 |
| **同一条 user 消息内前置** | **采纳** | 时间序还原；用户消息落在参考资料之后、指令之前；不新增消息条数，零兼容性风险；与 RAG「材料在前、问题在后」惯例一致 |

关键认知：extra parts 里的内容分两类——**参考资料**（群聊块/知识库结果/引用转述）和**指令**（插件 system_reminder，如「用户触发了XX」）。指令垫在用户消息后、靠近生成点是有效位置（Claude Code 即此模式），保持不动；真正错位的只有群聊块。挪走后用户消息身后从「最多 300 条群聊记录」变成「几行短指令」，注意力稀释的量级完全不同。

## 实现内容

### 拼装顺序（`astrbot/core/provider/entities.py`）

- `ProviderRequest` 新增字段 `leading_user_content_parts: list[ContentPart]`（前置内容块，语义：参考资料）。
- `assemble_context` 拼装顺序变为：

  ```
  leading（群聊上下文等参考资料）
  → 用户 prompt
  → extra parts（引用转述、知识库结果、插件 reminder 等指令/提醒）
  → 图片/音频
  ```

  副作用（正向）：用户消息与它自己的图片/音频变相邻。
- 简单格式降级条件补 `not self.leading_user_content_parts`：仅 prompt 时仍降级为纯字符串（向后兼容，行为不变）；有前置块时保持多模态块列表。

### 群聊块挂载点与提示词文案（`astrbot/builtin_stars/astrbot/group_chat_context.py`）

- `on_req_llm` 注入目标从 `req.extra_user_content_parts` 换成 `req.leading_user_content_parts`，其余注入逻辑（触发消息本身不注入、记录消费、延迟图片转述解析）不变。
- `GROUP_HISTORY_HEADER` / `GROUP_HISTORY_FOOTER` 重写为英文（让模型更确信是系统注入而非用户发言），并按新位置描述时间序。最终文案（初版过长过引导，已按「简单陈述」原则精简）：

  ```
  <system_reminder>
  You are currently in a group chat.
  --- BEGIN CONTEXT ---
  （群聊记录，旧→新）
  --- END CONTEXT ---
  Above is the group chat history before the current user message, arranged in
  chronological order. Below is the content of the current user message that
  immediately follows the chat history and needs to be processed.
  </system_reminder>
  ```

### runner 拼装条件（`astrbot/core/agent/runners/tool_loop_agent_runner.py`）

- 初始拼装判断补 `or request.leading_user_content_parts`：无 prompt、无媒体但只有前置块的边界情况也能进消息列表。

### 旁路核实（确认无需改动）

- re-query（`_resolve_tool_exec`）与主循环（`_iter_llm_responses`）传给 provider 的是 `run_context.messages`——初始拼装（runner 初始化时 `assemble_context`）已含前置块；且这两处都不传 `prompt`，而 openai/anthropic/gemini 三个源的 extra parts 只在 `prompt is not None` 时才被消费，本来就惰性。前置块随拼装结果自动走全链路。
- 知识库结果、引用转述等仍留在 extra（用户消息后）；将来想前置走同一字段即可，本次不动。

## 验证

- 新增 `tests/test_leading_content_parts.py`（运行 `python tests/test_leading_content_parts.py`）覆盖三点：
  - 拼装顺序：群聊块 → 用户消息 → 插件提醒 → 图片；
  - 纯文本降级：仅 prompt 仍是字符串，有前置块不降级；
  - 群聊钩子挂载点：块进 leading、extra 为空、触发消息本身不注入、header 含时间序说明。
- 既有 runner 回归 `tests/test_context_usage_snapshot.py` 通过。
- ruff（改动文件范围）通过。

## 部署注意

- 纯后端改动，更新后重启生效。
- 已落库历史消息不做迁移/回写：旧轮次里的群聊块保持原样（每条记录自带 `[昵称/时间]` 时间戳，可读），仅新请求按新顺序拼装。
- 插件生态无感知：`extra_user_content_parts` 的既有语义（追加在用户消息后）完全不变。
