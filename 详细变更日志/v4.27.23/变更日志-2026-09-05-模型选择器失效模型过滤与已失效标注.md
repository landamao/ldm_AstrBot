# [2026-09-05] 模型选择器失效模型治理：删除残留根因修复 + 只显示启用 + 失效引用标注「已失效」

> 本文件为独立变更日志，记录失效模型（已删除/已禁用）的完整治理：
> ① 修复已删除模型仍残留在各模型选择器的后端根因；
> ② 所有模型/提供商选择器的可选列表只显示启用的模型；
> ③ 已选中/引用过的模型失效后，界面显式标注「已失效」，不再静默显示原名。

---

## 一、问题现象与根因

### 问题现象

用户报告三个现象：

- **已删除的模型"有时候"还会出现在模型选择器里**：删除某个模型后，聊天页模型菜单、配置页各选择器里仍能看到它；时有时无——直到新建/编辑过其他模型或重启才消失；
- **已禁用（enable=false）的模型照常可选**：配置页提供商选择器、模型链选择器、知识库 embedding/rerank/文档清洗模型下拉里，已禁用的模型照常出现、照常能选（选了也用不了）；
- **选中的模型失效后无感知**：聊天页当前选中的模型、模型链里已配置的模型，被删除或禁用后界面照旧显示原名——用户不知道它已经用不了了，发消息失败时才反应过来。

### 根因（两条）

**1. 后端：`delete_provider` 漏同步内存配置（"已删除还出现"的根因）**

`astrbot/core/provider/manager.py` 的 `delete_provider` 用 `config["provider"] = [过滤后的新列表]` 删除——这是**把配置字典的键重新绑定到新列表**，而 `/api/v1/providers` 列表接口（`config_service.list_providers`）遍历的是 `provider_manager.providers_config`——它在 `__init__` 时持有的还是**旧列表的引用**，被删的 provider 还在里面。

这个引用断层其实早就被踩过、但只修了一半：`create_provider` 末尾特意写了同步（注释 "sync in-memory config for API queries"）；`update_provider` 走 `reload()` 会同步；`delete_provider_source` 也记得同步 sources——**唯独删除 provider 的两条路径（单删、删源连带）都漏了**。这正是"有时候还会出现"的原因：删除后到下一次触发同步（新建/编辑任意 provider）或重启之前，残留一直存在。

**2. 前端：多个选择器拉列表后不过滤 enable**

WebChat 模型菜单（`ProviderModelMenu`）一直有 `enable !== false` 过滤且每次打开强制刷新，是干净的；但 `ProviderSelector`（配置页提供商选择器）、`ChatModelChainSelector`（模型链选择器）、知识库四处（KBList / SettingsTab / DocumentsTab / alkaid）拉了列表直接用。另外 `RegenerateMenu` 虽有过滤，但菜单打开时 `loadProviderConfigs()` 不带 force，`providersLoaded` 一旦置 true 就不再刷新，与根因 1 叠加时同样残留旧数据。

## 二、设计定式（与用户确认，后续新增选择 UI 沿用）

- **禁用 = 失效 = 用不了**：不要拿"回显需要"当理由让失效模型留在选择器里；
- 所有模型/提供商**选择器（可选列表）只显示启用的**；
- **已选中/引用过**的模型失效时必须显式标注「已失效」，不能静默消失，也不能只显示裸 id；
- 失效判定 = 不在完整列表（已删除）**或** `enable === false`（已禁用）；**列表未加载完时不误报**。

## 三、实现

### 后端修复（一处，根治删除残留）

`astrbot/core/provider/manager.py` `delete_provider`：`config.save_config()` 后补 `self.providers_config = astrbot_config["provider"]`（与 `create_provider` 对称）。这一行落地后，"已删除还出现"在所有前端入口同时消失，不依赖前端改动。

### 前端过滤口径放在前端而非后端参数

后端 `/providers` 接口虽有 `enabled` 参数，但实现是 `bool(provider.get("enable", False))`——会把缺 `enable` 字段的旧配置当禁用误杀；前端 `!== false` 不会。因此统一**不传参、在前端过滤**，与 `ProviderModelMenu` 既有模式一致。

### 各组件改动

- `ProviderModelMenu.vue`（WebChat 模型菜单）：新增 `selectedProviderMissing` computed——`providersLoaded` 后，localStorage 里选中的模型不在启用列表中即判定失效，触发按钮上在模型名旁显示「已失效」badge（warning 色）。
- `ChatModelChainSelector.vue`（模型链选择器）：`isKnownProvider` 替换为 `isInvalidProvider`（禁用也算失效，原来的「已失效」chip 只对已删除生效）；链上主列表与对话框"已选模型"列表都显示 chip；可添加列表 `filteredProviders` 叠加 `enable !== false`；`providerList` 保持完整列表供失效判定（这是"判定用完整列表、过滤只加在展示 computed"模式的关键）。
- `ProviderSelector.vue`（配置页提供商选择器）：可选列表 `filteredProviderList` 叠加过滤；单选字段旁显示「已失效」chip（`currentSelectionInvalid`），多选在预览 chips 里逐个标注"（已失效）"；字段已有值时通过 watch 提前拉一次列表用于判定（否则要等打开对话框才能知道失效）。
- `RegenerateMenu.vue`（重新生成菜单）：两个菜单打开回调改为 `loadProviderConfigs(true)` 强制刷新，与模型菜单对齐。
- 知识库四处：`KBList.vue`、`SettingsTab.vue`、`DocumentsTab.vue` 下拉只显示启用的；`alkaid/KnowledgeBase.vue` 新增 `selectableProviders()`（5 处 v-select 的 items 用过滤版，完整列表仍供回显与判定），重排序模型文本回显改为 `rerankProviderDisplay()`：已禁用显示"模型名（已失效）"，已删除显示"id（已失效）"，未设置显示"未设置"。
- `zh-CN/features/provider.json`：新增 `models.invalidSelection` = "已失效"（`chatModelChain.missing` 本就是"已失效"，未改）。

### 踩坑：「已失效」chip 别包嵌套 div

给 `ProviderSelector` 字段区加 chip 时曾包了一层 `<div class="d-flex">`，导致 `.provider-name-text` 的 `max-width: calc(100% - 80px)` 参照从整行变成内层盒子，**正常模型名也被提前截掉约 80px 出省略号**（用户反馈"没有失效却早早显示省略号，后面还有很多位置"）。修复：去掉嵌套层，chip 用 `<template v-else>` 与文字**平级**插入，正常场景 DOM 与改动前完全一致。

## 部署 / 回归验证点

- **手动重启 ldm 生效**（后端同步修复必须重启；前端静态文件实时读盘，刷新页面即可）；
- 删除一个模型：聊天页模型菜单、配置页各选择器**立即**不再出现它（重启前删除仍会残留，属预期）；
- 禁用一个模型：配置页提供商选择器 / 模型链选择器"添加模型"列表、知识库各下拉不再出现它；模型管理页仍能看到并可重新启用（管理页语义不变）；
- 把当前聊天选中模型禁用/删除：聊天页模型按钮旁出现黄色「已失效」badge，模型链里该项出现「已失效」chip，alkaid 知识库重排序模型显示"模型名（已失效）"；
- 正常（未失效）模型的名称在配置字段、聊天页按钮上显示完整，无提前省略号；
- 重新启用失效模型：各处「已失效」标注消失、恢复正常可选。

## 回滚

还原上表 1 个 py 文件 + 8 个前端文件（vue/json），前端重新构建部署。后端回滚后"已删除模型残留"行为复现（需重启）。
