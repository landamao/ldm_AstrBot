# 修复：max_step 强制收尾时模型幻觉工具调用导致静默无回复并持久化悬空消息

- 日期：2026-09-05
- 上游 issue：[AstrBot#9912](https://github.com/AstrBotDevs/AstrBot/issues/9912)
- 上游 PR：[#9913](https://github.com/AstrBotDevs/AstrBot/pull/9913)（Open，未合入；本地按其方案实现并追加两层）

## 现象

Agent 达到 `max_step` 上限后，框架会移除全部工具（`req.func_tool = None`）并注入"请直接回复"的用户消息做强制收尾。如果此时大模型仍返回工具调用（幻觉输出，部分模型在无工具 schema 时也会继续输出工具调用格式）：

1. 本次运行**静默地不产生任何最终回复**，用户只看到卡住的"🔨 调用工具"状态；
2. 一条**协议非法的消息**（带 `tool_calls` 但没有配对 `tool` 结果的 assistant 消息）被持久化进对话历史；
3. 之后每一轮对话都会把这条残缺消息重新发给 Provider，OpenAI 兼容接口持续报 400。

## 根因链（本地 4.27.21 行号）

1. `astr_agent_run_util.py:181-195` 的 `run_agent` 与 `tool_loop_agent_runner.py` 的 `step_until_done`（`:1435-1448`，被 cron、第三方平台等使用）：强制收尾步置空 `func_tool`；
2. `tool_loop_agent_runner.py` `_handle_function_tools`（`:1502-1503`）：`if not req.func_tool: return` —— 生成器立即返回，不追加任何 tool 结果，也不做状态迁移；
3. 回到 `step()`：`tool_call_result_blocks` 为空列表仍无条件组装 `ToolCallsResult` 并 `run_context.messages.extend(...)`（悬空 assistant(tool_calls) 入上下文），状态停留 RUNNING，`final_llm_resp` 为 None；
4. `run_agent` 循环退出后 `done()` 为 False，不会 `set_result`，用户收不到最终回复；
5. `internal.py` `_save_to_history` 在 `llm_response is None` 时把含悬空消息的 `all_messages` 整段落库（标准路径 `:764-768` 无 `done()` 门槛）。

## 改动

### 层 1：`step()` 拦截幻觉调用（主修复，`tool_loop_agent_runner.py`）

在错误/停止检查之后、skills_like requery 之前：若 `llm_resp.tools_call_name` 非空且 `self.req.func_tool` 为空，视为幻觉调用——清空 `tools_call_name/args/ids/extra_content`，走现有 `_complete_with_assistant_response` 正常收尾（状态迁移 DONE、产生最终回复）。

追加（上游 PR 未含）：剥离后若 `completion_text` 与 `result_chain` 均为空（纯工具调用幻觉），补一条「（工具调用次数已达上限，未能生成最终回复。）」保证用户收到可见回复，避免"静默无回复"只修一半。

### 层 2：结果配对兜底（协议安全网，`tool_loop_agent_runner.py`）

组装 `ToolCallsResult` 之前，按 `tool_call_id` 逐个配对检查（数量相等不代表配对：一个调用可能产出多个结果块而另一个一个都没有），缺失的补占位 tool 结果：

> error: tool execution produced no result (tools may have been removed or the call was interrupted); ignore this call and answer based on the information gathered so far.

### 层 4：历史保护（`internal.py`，上游 PR 未含）

新增 `InternalAgentSubStage._drop_dangling_tool_call_messages`，在 `_save_to_history` 的 `_collect_messages_to_save` 末尾调用：丢弃带 `tool_calls` 但紧随的 `tool` 结果不足以按 id 配对的 assistant 消息及其残留结果组（部分配对的组整组丢弃，因为 tool 消息不能脱离其 assistant 存在）。既防再次落库，也顺带清理已中毒的存量会话（错误轮次的落库路径同样生效）。

未实现 issue 建议的层 3（`run_agent` 循环结束后仍未 done 时发送通用超时提示）：层 1 落地后幻觉路径必然正常收尾，层 3 针对的其余未收尾场景与本次修复正交，暂不引入。

## 测试

`tests/test_dangling_tool_calls.py`（脚本式，`python tests/test_dangling_tool_calls.py`），5 用例：

1. 幻觉调用按普通回复收尾：DONE 状态、有 llm_result、上下文与 `req.tool_calls_result` 无悬空消息；
2. 纯幻觉无文本时补上限提示，用户有可见回复；
3. 工具调用无结果块时按 id 补占位结果；
4. 结果块数量相等但 id 重复（call_a×2、call_b 缺失）仍按 id 配对补齐；
5. `_drop_dangling_tool_call_messages`：正常配对原样保留 / 无结果悬空丢弃 / 部分配对整组丢弃 / 混合场景只删悬空组。

回归：`tests/test_context_usage_snapshot.py`、`tests/test_tool_interrupt_context.py` 全部通过；ruff（改动文件范围）通过。`internal.py` 存在一个历史遗留的 I001（import 块相对/绝对导入混排），非本次引入，未处理。
