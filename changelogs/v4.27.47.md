# [4.27.47] — 2026-10-14 — 修复 v4.27.46 群聊刷屏回归 + 启动期内存治理

v4.27.46 上线后，在同一个群聊里部署了多个 ldmbot 实例的用户会遇到任何消息都引发刷屏、直到限流才停的严重回归（单机器人群只刷一轮，双机器人群互相触发成环）。根因是「handler 裸字符串自动发送」新特性与既有的装饰器堆叠行为叠加：`@filter.platform_adapter_type` 叠在 `@filter.llm_tool` 下时会把 LLM 工具函数同时注册成普通消息事件处理器（历史行为，对每条 aiocqhttp 消息无条件激活），此前这些误激活的返回值被静默丢弃，v4.27.46 起却被自动当作回复发出，机器人互相喂消息直到限流。本版本回滚该特性。另集中处理启动期内存占用：此前实测尚未处理任何一条消息，仅「导入核心 + WebUI」就要吃掉 250 MB 常驻内存，加上插件与 provider 实例化后稳态约 357 MB，而峰值私有提交高达 2831 MB。逐项归因后发现三处与业务无关的开销：三家 LLM SDK 仅被用来写类型注解却全量加载、知识库解析器在未建库的实例上也照常导入、numpy/faiss 按 16 核创建线程池各预留数百 MB 至 2 GB 提交内存。本版本把前两类改为按需导入、把线程池默认收敛到单线程，核心导入基线降到 156 MB，提交内存从 2916 MB 降到 11 MB 量级。

## 🐛 修复（1项）

### 1. 回滚「handler 裸字符串自动发送」，修复群聊刷屏回归

`astrbot/core/pipeline/context_utils.py` 的 `call_handler` 中，v4.27.46 新增的裸字符串分支（`yield "文本"` / `return "文本"` 自动按 `plain_result` 发送）被整体移除，恢复 v4.27.45 行为：裸字符串产出回到静默丢弃，插件需照旧写 `yield event.plain_result("文本")`。

触发链路（详细根因见「详细变更日志/v4.27.47/」）：插件把 `@filter.platform_adapter_type` 叠写在 `@filter.llm_tool` 之下时，装饰器自下而上执行，前者先以「普通消息事件处理器」类型注册了该函数且唯一过滤器对 aiocqhttp 消息无条件放行；后者复用同一条注册记录但没有纠正事件类型。于是每个 LLM 工具函数同时是「每条消息都会激活的 handler」，被误调用时工具参数为空字符串，命中提前返回分支产出提示文案（如「请输入task参数（任务描述）」「Hermes 适配器状态…」），v4.27.46 起这些文案被自动发出。单机器人群只刷一轮；同群双机器人时 A 的输出成为 B 的新消息、B 又被激活发出，互相触发直到限流。回滚后误激活的返回值重新被静默丢弃，刷屏不可能发生。

注意：误激活本身（LLM 工具被当消息 handler 空跑）是上游历史行为，本版本未动；如需根治需调整装饰器堆叠的注册语义，影响面大，留待后续单独评估。相关测试 `tests/test_yield_plain_str.py` 一并移除。

## ⚡ 性能优化（3项）

### 1. 启动期不再加载三家 LLM SDK（省约 86 MB）

`astrbot/core/provider/entities.py` 在模块顶层导入了 `openai`、`anthropic`、`google.genai` 三家的响应类型，而这三个名字只出现在 `LLMResponse.raw_completion` 的类型注解里。该文件已启用 `from __future__ import annotations`（注解不求值），全代码库也没有任何一处 `get_type_hints`，因此这三行导入属于纯浪费：实测它们在已加载核心的前提下边际占用分别为 27.7 MB、19.6 MB、64.9 MB，合计 112 MB。

现改为放进 `if TYPE_CHECKING:` 块。**核心导入基线从 250.0 MB 降到 156.3 MB**。SDK 不再消失——首次真正使用对应 provider 时由 `provider/manager.py` 的动态导入按需加载，行为与功能完全不变。

对只配置 OpenAI 兼容接口的实例，净省约 60 MB（`openai` 会在 provider 实例化时加载回来，`anthropic` 与 `google.genai` 则彻底不再加载）。

### 2. 知识库解析器按需导入（省约 14 MB）

`knowledge_base/parsers/pdf_parser.py` 顶层导入 `pypdf`（边际 11.3 MB）、`knowledge_base/retrieval/tokenizer.py` 顶层导入 `jieba`（边际 2.5 MB）。两者都只在解析 PDF 与中文分词时才用得上，而多数实例并未启用知识库，却要为它们付出常驻内存。现改为在 `parse()` 与 `tokenize_text()` 内部导入，导入结果由 `sys.modules` 缓存，重复调用无额外开销。

### 3. 数值库线程池默认收敛到单线程（提交内存 2916 MB → 11 MB）

numpy 与 faiss 在首次导入时会按 CPU 核数创建 OpenMP / OpenBLAS 线程池，每个线程预留一大块私有内存。16 核机器上实测：

| 库 | 默认线程数 | 单线程 |
| --- | --- | --- |
| `import numpy` | 提交约 490 MB | 约 9 MB |
| `import faiss` | 提交约 2424 MB | 约 17 MB |

这些内存不计入常驻工作集，但会占满提交限额、推高页面文件占用并触发系统内存压缩（本机 `MemCompression` 已达 473 MB）。机器人的向量检索与相似度计算都是小规模运算，多线程收益接近于零——实测 533 条向量、4096 维的表情包索引在单线程下检索正常。

新增 `astrbot/utils/runtime_env.py` 的 `apply_thread_env_defaults()`，在 `main.py` 与 CLI（`astrbot/cli/commands/cmd_run.py`）两条启动路径上、`.env` 加载之后、任何 numpy/faiss 导入之前调用，用 `setdefault` 把 `OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` 设为 `1`。**用户可在 `.env` 里显式设置覆盖**（`setdefault` 不覆盖已有取值），需要并行重计算的场景调大即可。
