# [4.27.42] — 2026-10-07 — 空艾特去特殊化：回归普通消息唤醒逻辑

空艾特（只 @ 机器人、不带任何内容）原先由一条独立的特殊逻辑处理：绕开正常管线直接请求 LLM 回复一句，再开一个 60 秒的等待窗口，把该用户下一条消息拼上 @ 后重新投递。这条路有两个问题：一是与群聊上下文增强完全脱节——空艾特的请求不经过正常管线，上下文注入不生效；二是与「只 @ 机器人是否触发等待」开关互相冲突——关闭开关后空艾特更是彻底无响应。本版本把空艾特完全回归普通消息：正常唤醒、正常进入 LLM 管线，群聊上下文增强等所有既有机制照常生效，不再有任何特殊分支。

## ✨ 体验优化（1项）

### 1. 空艾特与仅唤醒前缀消息按普通消息处理

空艾特、空 @ 全体成员、只发一个唤醒前缀（如只发「小助手」）这类「唤醒了但没说内容」的消息，现在与普通消息走完全相同的路径：唤醒判断不变（@ 机器人即唤醒），进入 LLM 请求前由管线自动补一条 system_reminder 提示词（说明用户 @ 了你但未输入内容，请结合对话上下文回应），然后照常请求 LLM。开启群聊上下文增强后，空艾特即可联系群里正在聊的内容回应——与普通艾特行为完全一致，不再有任何分叉。

- 不再有 60 秒等待窗口：空 @ 之后单独再发的语音/图片就是两条独立消息，按各自的唤醒规则处理。
- 提示词随 message_str 落库，本次请求与会话历史内容一致（与消息防抖合并时的 system_reminder 做法对齐）。
- 空艾特消息本身不含文本/图片/Json 组件，不会被记入群聊上下文历史，不污染后续注入。
- 判定边界：@ 了别人、空艾特同时携带图片/语音/文件/引用等组件、私聊纯空白消息、未唤醒事件，都不算空唤醒，按原有逻辑处理。

## 🛠️ 问题修复（1项）

### 1. 关闭「只 @ 机器人是否触发等待」后空艾特完全无响应

原先空艾特的 LLM 回复依赖该开关开启；关闭后空艾特虽然正常唤醒，却在 LLM 请求前被「空消息跳过」判定拦下（无文本、无媒体、无引用即跳过请求），表现为 @ 机器人毫无反应。现在空唤醒统一在管线内补提示词后正常请求，与该开关彻底解耦——该开关也随本次改造移除，不再存在配置面。
